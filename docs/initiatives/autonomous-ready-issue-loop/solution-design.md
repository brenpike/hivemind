# Solution design: Lair — Software Factory

This is the solution design for the Lair, epic #603. It covers the HOW that the slices share. It links the [PRD](../../prds/autonomous-ready-issue-loop.md) and [ADR-0045](../../adr/0045-lair-software-factory.md) rather than restating them, cites them as "ADR-0045 decision N", and adds only what they lack. The design review is recorded in the [review record](review-record.md).

Three part designs govern parts of this design: [strain launch](strain-launch-design.md) (#630), the [merge lane](merge-lane-design.md) (#631) and [claim integrity](claim-integrity-design.md) (#632). Each part this design hands to one of them is a link to the part design and section that govern it. Where several part designs govern one place, the text names the aspect each one governs. Seams between the part designs, under Contracts and seams, states how they fit where they disagree. Each part design is frozen: a change to one lands only with a dated entry under Amendments here, which edits this stamped design and so stales the review record. #646's design, once its own review passes, joins this design as a fourth part design through a dated entry under Amendments. That entry links it from Seams between the part designs, item 6, and adds it to the Part designs column of #604, #608 and #612, and the overlord adds #646's design to the Initiative line of #604, #608 and #612, a body edit that keeps every other byte. From then on it is frozen like the other three.

## Context and code truth

The Lair builds on this code, as it stands on trunk:

- `plugin/skills/spawn-brood/scripts/spawn-brood.sh` starts each strain as a detached tmux session running `claude` in auto mode in its own worktree. It copies the coordinator's `.claude/settings.local.json` into every strain worktree. What its per-brood settings file holds is in [strain launch](strain-launch-design.md), Context and code truth, "Correction to the parent design".
- `plugin/skills/brood-status/scripts/brood-status-collect.sh` reports, per strain, whether the tmux session is alive, the pull request state and the run ledger state. It reads no run result, so for the Lair it gives liveness only: it cannot tell a run end, a park or a stall apart.
- `plugin/skills/github-review-loop/scripts/merge-approved.sh` is the only merge path. It reads `HIVEMIND_AUTO_MERGE` (the merge method) and `HIVEMIND_AUTO_MERGE_ADMIN` (by presence) each time it runs. Its tests are `tools/test_merge_approved.sh`.
- `plugin/workflow-src/lib/decide.js`, with `plugin/references/decision-autonomy-table.json`, has the levels `high`, `balanced` and `low`. An unknown level resolves to `low`. Its only actions are `take` and `ask`. There is no `unattended` level and no park action.
- `plugin/hooks/hooks.json` holds `PreToolUse` hooks only. There is no `Stop` hook.
- `plugin/agents/overlord.md` holds the `## Instinct` path, which asks the user which delivery path to take, and the `## Resume On Start` path. It also holds the default post-PR watch under `## Review Remediation Posture`.
- `plugin/skills/triage-backlog/scripts/triage-ops.sh` defines the `readiness:*` labels and `type:epic`. It defines no `lair:*` family.
- `plugin/skills/prd-to-issues/scripts/subissue-ops.sh` creates the epic and attaches slices as native sub-issues through the GraphQL `addSubIssue` mutation. It creates no native blocked-by link: `plugin/skills/prd-to-issues/SKILL.md` writes blocked-by as `#N` refs in a slice's `## Dependencies` section.
- The standard-delivery launch in `plugin/workflow-src/standard-delivery/main.js` already takes settled decisions and a draft flag. `decisions` is a list of 1 to 10 non-blank strings of at most 2000 code points each, held as `run.decisions`. `draft` is a boolean that defaults to false.
- No readiness check exists yet. It is built under #615.
- Nothing under `plugin/` reads `HIVEMIND_LAIR_STRAIN` or uses a `lair:*` label.

## Components

### Strain launch and settings

Built by #604. [Strain launch](strain-launch-design.md) governs it: Components "Strain launch and settings", "Launch inputs" and "Start points".

### Strain result and liveness

Built by #604. Each aspect has its own governing part:

- the result and the liveness files: [strain launch](strain-launch-design.md), Components "Strain result and liveness";
- crash and stall detection, built by #608: [claim integrity](claim-integrity-design.md), Design invariants (Claim state) and Lifecycle (the run checks), with the idle signal of Seams between the part designs, item 13;
- when the Lair removes a run's worktree: never before the run's outcome marker is written, per the [merge lane](merge-lane-design.md), Contracts and seams "Lair pull request" (Result recording) and Decided for you (R37), nor before its digest entry is written, a wait #611 builds (Seams between the part designs, item 14), with strain launch's Lifecycle step 5 after it.

### Unattended autonomy level

Built by #607. It adds the `unattended` level to the autonomy table and the park action to `decide()`. The level is selected only by `HIVEMIND_LAIR_STRAIN` (ADR-0045 decision 6). The engine builds the park record and its key (Contract "Park record") and the agent-call cap ([strain launch](strain-launch-design.md), Components "Launch inputs", "Agent-call cap"). The governance and agent edits that replace the overlord's Instinct fallback, Resume On Start question and post-PR watch for a verified strain are under [strain launch](strain-launch-design.md), Components "Unattended governance edits". Park types follow ADR-0045 decision 7, and the architectural gate follows ADR-0045 decision 8. When the marker is absent and the checkout holds no `.hivemind/lair/launch.json`, the levels and actions are today's; with that file and no marker, every script fails closed (strain launch, Contracts and seams, "Marker check").

### Controller tick and admission

Built by #608. The controller is a deterministic script in a tmux window (ADR-0045 decision 2). #608 covers:

- the tick loop, in the one tick order under Seams between the part designs, item 5;
- the single-instance lock, the claim, the readiness-check call, the injection scan, labels and marker comments, the halt file, the wall-clock budget, the start-up sweep and the queue report, which [claim integrity](claim-integrity-design.md) governs: its Components and Lifecycle;
- the change to `triage-ops.sh` so that triage leaves `lair:*` issues alone (ADR-0045 decision 16).

The no-open-blocker condition of admission reads native blocked-by links only (ADR-0045 decisions 2 and 10). The readiness check reads `## Dependencies` refs only to require their edges.

### Merge lane and auto tier

Built by #605. The [merge lane](merge-lane-design.md) governs it: Components "Merge-lane step of the tick", "Settle check" and "Auto-tier script", and Contracts and seams "Lair pull request", which holds the lane rule.

Per the user's answer 2A of 2026-11-22, the auto-tier script's fixed floor (merge lane, Components "Auto-tier script", "The floor") also holds the directories `docs/prds/`, `docs/initiatives/` and `docs/adr/`, built by #605. Each matches at the repository root, compared ignoring ASCII case, as the rest of the floor. So ADR-0046's rule that a docs pull request never takes the Lair's auto tier holds in every consumer project, whatever its `.github/lair.json` lists.

### Park answer round trip

Built by #609. A park writes the park marker comment. Its form and signature follow [claim integrity](claim-integrity-design.md), Contracts and seams ("Marker comment", "Counting rule"), and its label moves follow claim integrity's Lifecycle (run end), for a remediation run's park too, in the write order of Seams between the part designs, items 8 and 10. An answer counts only as ADR-0045 decision 11 states, against a counting park marker. Relabeling `readiness:ready` re-admits the issue. The Lair alone builds the settled decisions from the answers ([strain launch](strain-launch-design.md), Contracts and seams, "Settled decisions"), and the re-claimed run continues on the pushed branch (strain launch, Start points), from the pre-image in the park marker of the claim whose counting outcome marker is the issue's latest, with outcome `parked` (Seams between the part designs, item 1), after the re-claim checks of item 15. A third park, or an `approval` park, hands the issue off (ADR-0045 decision 7).

### Post-PR remediation strains

Built by #610. The tick polls each open Lair pull request. What starts a remediation is Seams between the part designs, item 2. Each aspect has its own governing part:

- the dispatch, the launch, the settings, the author filter and the result contract: [strain launch](strain-launch-design.md), Components "Remediation strain launch";
- the markers, the park route, the halt and the outcome mapping of each remediation run, which the merge lane calls a fix-up run: the [merge lane](merge-lane-design.md), Components "Fix-up runs" and Lifecycle "Run outcome to labels", under Seams between the part designs, items 2, 3 and 10.

### Decision digest and circuit breaker

Built by #611. Each Lair session produces a digest of every decision taken for the user, with its issue and pull request (ADR-0045 decision 14). The digest's requirement is its row under State and ownership. #611 designs the rest during its build, as Seams between the part designs, item 14, states.

The circuit breaker follows [claim integrity](claim-integrity-design.md), Components "Halt file and circuit breaker" and its Lifecycle rules for the halt and the breaker, with the outcomes it counts and skips under Seams between the part designs, item 4.

### Release-train versioning mode

Built by #606. It is the opt-in mode of ADR-0045 decision 15: each pull request adds a change fragment, and a script-built release pull request applies the highest bump. Its open choices are settled through #647, a design issue that blocks #606, as recorded under Decisions.

### Parallel strains

Built by #612, after #606. More than one strain runs at once, only where the containment of Seams between the part designs, item 6, is confirmed, as #646 designs it. Parallel Lair pull requests merge in sequence, each up to date with trunk and green on its merged head, per the PRD's Parallelism criterion.

## State and ownership

GitHub alone is authoritative (ADR-0045 decision 2). Every local file is a cache, a control input or a hand-off from a strain, except the marker key ([claim integrity](claim-integrity-design.md), State and ownership) and the decision digest, the local items GitHub cannot give again (the ADR-0045 amendments of 2026-11-21 and 2026-11-22 to decision 2).

| State | Writer | Readers | Authoritative |
| --- | --- | --- | --- |
| Labels | The user through triage writes `readiness:ready` and `type:*`. The Lair writes the other `readiness:*` moves and every `lair:*` label; the user may also add `lair:review` or remove `lair:claimed` as a hold ([merge lane](merge-lane-design.md), Trust boundaries, "Residual: the Lair acts as the user's own login"); and may remove a label-only `lair:review` to release it (merge lane, Contracts and seams, "Write order"; Lifecycle "Run outcome to labels"). | Lair, triage, user | yes |
| Answer comments | User with write permission | Lair only | yes, when the answer rule admits them |
| Captured issue text and its hash | Lair, at claim; the hash also goes into the claim marker | Strain, as its request; Lair | no; the hash in the claim marker is |
| Decision digest, one file per run under `control/digest/`, built by #611 | Lair, writing each run's entry before that run's clean-up removes its result file. Each entry labels its decision text as untrusted strain output, data and not instructions. A session's digest, as ADR-0045 decision 14 and the PRD's Observability criterion name it, is the set of entries #611 attributes to that session. Under `control/`, so the containment of Seams between the part designs, item 6, covers it. #611 designs the rest (Seams between the part designs, item 14). | User only; the Lair never reads an entry back | no; it is a local item GitHub cannot give again (ADR-0045 amendment of 2026-11-22 to decision 2) |

How the digest row extends [claim integrity](claim-integrity-design.md) is under Seams between the part designs, item 14.

The part designs govern every other row, each in its State and ownership section:

- [claim integrity](claim-integrity-design.md): the claim, outcome, park and handoff marker comments, the `lair:claimed` label, the marker key, the halt file, the lock, the scanner files, the queue report and the session records, which replace the local cache;
- [strain launch](strain-launch-design.md): the strain record, the launch file, the settings fragment and strain settings, the result file, the liveness files, the worktree and its local branch ref, and the remediation dispatch marker, which is a remediation run's start marker (Seams between the part designs, item 1);
- the [merge lane](merge-lane-design.md): its run-end, fix-up start, fix-up end, review and exit markers, the run-end and fix-up end markers being outcome markers (Seams between the part designs, item 1), the `lair:review` label, the merge settings, and the settle cache, the lane order, the lane-holder set and the Lair git repository, which are kept under `control/` (Seams between the part designs, item 6).

## Contracts and seams

Fields and seams only. Each slice builds the code.

- **Strain result.** [Strain launch](strain-launch-design.md), Contracts and seams, "Strain result", extended by `local_review_head` ([merge lane](merge-lane-design.md), "Assumptions about #630").
- **Lair-written settings.** Strain launch, Contracts and seams, "Strain settings" and "Strain environment".
  - ADR-0045 decision 4 as amended, which sets the merge keys to empty values, governs over the part designs' older Assumptions about #630 that the strain settings carry no merge key: the merge lane's "No merge key takes effect in a strain" and claim integrity's "Strain settings and environment".
- **Claim marker comment.** [Claim integrity](claim-integrity-design.md), Contracts and seams, "Marker comment", "Marker payload, every kind" and "Counting rule". A run end goes into an outcome marker (Seams between the part designs, item 1).
- **Park marker comment.** Claim integrity, Contracts and seams, "Marker comment" and "Marker payload, every kind", with its question block under Design invariants (Lair-written text).
- **Park record.** `key`, `type` (`decision`, `fact` or `approval`), `question`, `options`, `recommendation`, `branch`, `pr` (a draft pull request or null).
  - The engine builds the `key` from the stop's identity fields, all of them engine data and never model text: the stop kind; the step, the cause code and the sorted paths, which are ADR-0045 decision 6's cause identity; and, for a stop that is not a step stop, the fixed id of the `decide()` site that made it.
  - The `key` is the fixed prefix `park`, then `-`, then the first 16 hex characters of the SHA-256 of the canonical JSON array of those fields. So it always matches `^[a-z0-9][a-z0-9-]{0,63}$` (claim integrity, Design invariants, Lair-written text), whatever case or characters the fields hold.
  - So the same stop on a re-claim of the same issue gives the same key, whatever the question's wording, and two step stops with distinct identities give distinct keys. For a stop that is not a step stop, the key is distinct per `decide()` site only: two stops from one site share it, and an answer binds to the park marker it follows (ADR-0045 decision 11).
- **Answer form.** `/lair answer <key> <option or text>`. `<key>` names an open park on that issue. A `decision` answer names one option. A `fact` answer is free text.
- **Settled decisions.** Strain launch, Contracts and seams, "Settled decisions".
- **Auto-tier script result.** The merge lane, Components "Auto-tier script".
- **Readiness-check call at claim.** Claim integrity, Contracts and seams, "Readiness-check call at claim".
- **Queue report.** Claim integrity, Contracts and seams, "Queue report".

### Seams between the part designs

Where the part designs disagree, these rules decide. Each names its source.

1. **Markers.** Built by #605, #608, #609 and #610: #605 builds the marker format and verifier, and each builds the markers it writes. Every Lair marker is append-only and signed, and is posted on the claimed issue ([claim integrity](claim-integrity-design.md), Contracts and seams, "Marker comment" and "Counting rule"; Decisions, "Markers are append-only"). Their payload is claim integrity's (Contracts and seams, "Marker payload, every kind"), with these additions:
   - Three more kinds: `fixup-start`, a remediation run's start marker, which is also strain launch's remediation dispatch marker, with `run` the remediation run's id; `review`, the merge lane's review marker; and `exit`, its exit marker. Each carries the nonce of a counting claim marker on the same issue, as an `outcome` or `park` marker does under the counting rule.
   - The [merge lane](merge-lane-design.md)'s run-end and fix-up end markers ("Markers the merge lane writes") are `outcome` markers. They carry the fields the merge lane names for that end, and `outcome` also takes the values `no-pr`, `invalid-result` and `not-launched`.
   - The merge lane's field names map onto claim integrity's: `claim_nonce` is `nonce`, `run_nonce` is `run`, and `claimed_at`, `started_at` and `dispatched_at` are `at`. The merge lane's start-marker `kind`, `fixup-checks` or `fixup-review`, is not carried, since under item 2 no rule reads which trigger started the run.
   - For a remediation, strain launch's own `claim_nonce` (in its dispatch marker, settings marker, launch file and result) is `run`. The marker's `nonce` is the nonce of the claim whose run-end marker recorded the pull request.
   - A parked remediation run's end marker carries, of the park, only its `key` and `type`, as claim integrity's invariant Lair-written text holds for a signed park payload. The park text goes only into the park marker's question block, the slot. The merge lane's "or the park record when parked" (Contracts and seams, "Markers the merge lane writes", the fix-up end marker) and "the fix-up end marker with the park record" (Lifecycle "Run outcome to labels") no longer apply.
   - The `park` payload of a park that pushed commits (strain launch, Components "Start points", "A park after commits pushes"), or of a run whose start kind is re-claim or remediation, whose start commit the remote held at launch, also carries `branch`, which passes the identifier gate and is at most 255 bytes, and `head`, 40 or 64 lowercase hex digits, from the parked result. When the remote has moved since, the next re-claim's moved-head check hands the issue off with reason `branch-moved` (item 15). This overrides claim integrity's "carries only `key` and `type`" for these two validated tokens. #609's re-claim reads its pre-image, the parked branch and head of strain launch's Start points, from the park marker of the claim whose counting outcome marker is the issue's latest, with outcome `parked`.

   [Strain launch](strain-launch-design.md)'s single write of the outcome, `ended_at`, the baseline and, after a remediation, the end head ("Assumptions about #632") is one appended outcome marker, never an edit of the claim marker. Strain launch's remediation dispatch marker is posted on the issue. Claim-time fields, such as `design_stamps`, go in the claim marker.
2. **What starts a remediation.** Built by #610. This design calls a remediation strain's run a remediation run, as the PRD and strain launch do. The merge lane's fix-up run names the same run, and its fix-up start and end markers are the remediation run's start and end markers. One remediation strain per pull request, the user's 2026-11-22 answer in strain launch (Components "Remediation strain launch"; Decisions), decides what starts a remediation, from review feedback or a red CI result. The merge lane's fix-up runs are those runs. They keep their start and end markers, their park route and their outcome mapping (merge lane, Components "Fix-up runs" and Lifecycle "Run outcome to labels"). A pull request whose one remediation has started gets no second, whatever starts it:
   - The one remediation is spent once its start marker lands. A dispatch whose start-marker write did not land wrote nothing, and a later tick may dispatch, since strain launch dispatches only when the pull request has no dispatch marker.
   - The merge lane's rows govern a `parked`, `crashed`, `stalled` or `timed-out` remediation end (Lifecycle "Run outcome to labels"). Strain launch's requirement that such an end routes the pull request to `lair:review` (Components "Start points", "Handling by start kind") is met by the claim end, which stops every merge (strain launch, Components "Remediation strain launch", "Tick order"; merge lane, Contracts and seams, "Lair pull request").
   - A start marker that landed with no launch ends `not-launched`, which makes a batch review: `lair:review` on the issue and the pull request, then a review marker with reason `fixup-not-launched`, then the fix-up end marker last (item 8). The merge lane's rule that a `not-launched` end writes only the end marker, and its new run after that end, no longer apply.
   - The CI-red rule (Q9) never starts a second run. Its step 1 holds for any remediation start marker under the claim, whichever trigger wrote it, and its step 3 starts a run only when the pull request has no start marker.
   - The merge lane's start precondition that the issue's budget has time left, and its `budget-exhausted` route, no longer apply to a remediation run (item 3).
   - Under the halt or a tripped breaker a due dispatch starts no run (merge lane, Lifecycle "Stage 4: halt and circuit breaker"). It does not block the merge lane's step 9: the review wait still sends the pull request to batch review with reason `review-wait-elapsed`.

   The merge lane's R2, no cap on fix-up runs, no longer applies.
3. **A remediation run's budget.** Built by #608, which builds the budget check, and #610, which records each remediation run's launch time. A remediation run's wall-clock budget is timed from its own launch (claim integrity, Lifecycle, the budget check; Decisions). This replaces the merge lane's timing of a fix-up run from the claim marker's `claimed_at`, with its start precondition on the issue's budget and its `budget-exhausted` route.
4. **The circuit breaker.** Built by #611. The breaker:
   - counts `failed`, `crashed`, `stalled`, `timed-out` and `invalid-result` outcomes, as the PRD's Stop controls criterion and the [ADR-0045](../../adr/0045-lair-software-factory.md) amendments of 2026-11-22, "more causes stop the Lair" and "the circuit breaker counts invalid results", state;
   - also counts, as a failure, a run this session ended whose outcome marker does not count, a refinement neither the PRD nor ADR-0045 states, decided in claim integrity (Decisions, the breaker and its window, C3-2);
   - skips `parked`, `blocked`, `no-pr` and `not-launched` outcomes, which neither count nor end a streak; `blocked` stays skipped, as both the merge lane and claim integrity skip it;
   - records an invalid result as the outcome `invalid-result`, never `crashed`, so strain launch's Failure modes row "Invalid result", "Treated as a crash.", no longer applies to the outcome value;
   - ends a streak on a `complete` outcome of a run end under a live claim, the merge lane's qualifier ("Stage 4: halt and circuit breaker");
   - neither counts nor ends a streak on a remediation run end under a claim that already has a terminal outcome;
   - covers only runs this Lair session launched.

   This one set replaces the merge lane's ("Stage 4: halt and circuit breaker") and claim integrity's (Lifecycle, the breaker) separate lists. For invalid results it also replaces the Breaker column of the merge lane's Lifecycle "Run outcome to labels", which reads "neither" in its rows "Delivery invalid result" and "Fix-up `blocked`, or an invalid result", and the breaker clauses of the merge lane's Failure modes rows "Invalid result" and "Failed fix-up run". The rest of the breaker follows claim integrity.
5. **One tick order.** Built by #608. Run end and the run checks, then the remediation step (strain launch, Components "Remediation strain launch", "Tick order"), then the merge lane (merge lane, Components "Merge-lane step of the tick"), then claims. In claim integrity's tick (Lifecycle), steps 1 and 2 still come first, the remediation step and the merge lane run in step 3 after the run checks, with park answers after the merge lane, and claims are step 4.
6. **Containment of the key, the halt file and the Lair's tmux servers.** Built by #604, with #608's probe `sandbox` and #612's gate on running strains at once. The requirement is what the part designs and ADR-0045 already state:
   - No session the Lair starts, strains and remediation strains included, can read, write or delete anything under the `control/` folder of the Lair's state root, by any tool ([claim integrity](claim-integrity-design.md), "Assumptions about #630", Containment of the key and the halt file), or reach the tmux server that holds the Lair's own window or the scanner's server on `control/scan.sock` (Tmux reach).
   - On Linux each strain and remediation strain runs in a sandbox with its own process namespace (claim integrity, "Assumptions about #630", Process reach). Where the platform offers no such sandbox, macOS among them, the [ADR-0045](../../adr/0045-lair-software-factory.md) amendment of 2026-11-22 on process reach applies, and a Lair-started session that escapes its containment can sign markers that count, under the ADR-0045 amendment of 2026-11-21 on forged markers.
   - Per the user's answer A of 2026-11-22 to the key-containment question and answer 1A of 2026-11-22 at this design's integration review round 1, #604 builds this containment per platform, and the Lair starts no strain without it. #608's environment preflight (strain launch, Components "Strain launch and settings") gains the probe `sandbox`: when containment cannot be confirmed, the Lair claims nothing and stops with cause `strain_env_preflight`, probe `sandbox`.
   - How #604 meets the requirement is designed in #646, Lair design: strain containment, which blocks #604, #608 and #612: the mechanism per platform, the hiding of sockets and buses, isolation between strains, the write allowlist, the cases of the probe `sandbox`, the fallback for a keyring the sandbox hides, and where #612 runs strains at once. #646's design, once its own review passes, joins this design as a fourth part design through a dated entry under Amendments. That entry links it from this item and adds it to the Part designs column of #604, #608 and #612, and the overlord adds #646's design to the Initiative line of #604, #608 and #612, a body edit that keeps every other byte. From then on it is frozen like the other three.
   - The merge lane's cache, that is the settle cache, the lane order, the lane-holder set and the Lair git repository, sits under `control/`, so the containment of `control/` covers it. #605 names its folder there; `control/cache/` still holds only the queue report.
   - Strain launch's named residuals stand as written (Trust boundaries), "a prompt-injected strain holds the user's rights" and "the tmux global environment" among them. Of a strain's own result, the merge lane's result checks bound its `pr`, `branch` and `head` (Contracts and seams, "Lair pull request"); its outcome, park record and decisions are not bounded and stay under the first of those residuals.
   - Claim integrity's assumption "Result file per strain" and the merge lane's assumption that a strain writes nothing outside its worktree and the shared object and ref store ("Assumptions about #630") are requirements #646 designs for. Where they do not hold, the merge lane's residual "A strain that writes the tick's inputs" applies (Trust boundaries).

   Strain launch's statement that a strain can read any file the user can read (Contracts and seams, "Strain environment"; Trust boundaries) holds outside what this item denies.
7. **Orphans and the start-up sweep.** Built by #608. The orphan rule and the start-up sweep follow claim integrity (Design invariants, Claim state; Components "Reconciler and start-up sweep"; Lifecycle). A strain whose kept worktree holds a valid result file whose outcome is unwritten is exempt: the sweep keeps it (strain launch, Components "Remediation strain launch", "A deferred write is not a budget overrun or an orphan"). The Lair removes a run's worktree only after that run's outcome marker is written (merge lane, Decided for you, R37) and its digest entry is written, a wait #611 builds (item 14), and then as strain launch's Lifecycle step 5 states. That step's `unpushed_head` is not written to GitHub, since clean-up comes after the outcome marker, which is never edited: the kept worktree is the record, and the queue report reads it locally. Step 5's "records `unpushed_head` in the claim outcome" no longer applies.
8. **Run-end write order.** Built by #608 for the run end and park routes, #610 for the remediation run end, and #605 for the exit and batch review routes; #609 builds the `gh pr ready` of a completed re-claim. Every route that makes more than one write takes the merge lane's Write order (Contracts and seams, "Write order"): a run end, a remediation run end, an exit, a park, a batch review and a run-end handoff (item 15). A route's label changes and pull request changes come first, then its markers, and the marker that ends the route last. A run-end handoff writes its labels and pull request changes, then its handoff marker, then the outcome marker last.
   - A re-claim refusal at admission, before any claim marker, is not a route of this item. It follows claim integrity's claim sequence order, the handoff marker and then the label (Lifecycle, claim sequence step 4).
   - A run's result file stays in its kept worktree until that last marker lands, so a later tick computes the route again from it and repeats the writes, each idempotent (strain launch, Lifecycle step 5). A run check with no result file computes its route again from the session, the worktree and the clock.
   - Strain launch's `gh pr ready` after a `complete` re-claim result whose pull request is a draft (Components "Start points") is a pull request change made before the run-end mapping reads the draft flag. When it fails, the pull request goes to `lair:review`, as strain launch states.
   - Claim integrity's order at run end and in the run checks (Lifecycle), the outcome marker first and then the labels, no longer applies. Each write still re-reads its guards under claim integrity's invariant Write guards, and the run checks end the session after the outcome marker.
9. **The pull request of a delivery run that did not complete.** Built by #608. Strain launch routes to `lair:review` the pull request of a delivery run that ended `blocked`, `failed`, `crashed`, `stalled`, `timed-out` or with an invalid result (Contracts and seams, "Assumptions about #631"; Failure modes). That route applies only to a pull request that passes the merge lane's Lair pull request checks other than the head: the same repository, not a fork; the trunk base; the Lair's own login as author; and the claim's branch. The Lair leaves any other pull request alone, as the merge lane's "Recorded residual: a pull request no result names" states.
   - The claim's branch is the result's `branch` when the result passes the schema check. Otherwise it is the branch checked out in the run's kept worktree, read at run end. The strain controls that branch, but the route only adds a batch review, and the pull request must still pass the other checks of this item. With neither, the pull request falls under that recorded residual.
10. **Labels of a remediation run's park.** Built by #610. Claim integrity's rule that an answerable park keeps `lair:claimed` (Lifecycle, run end) applies to a remediation run's park too. The merge lane's removal of `lair:claimed` in its fix-up park rows (Lifecycle "Run outcome to labels") no longer applies. The claim still ends, through the remediation run's end marker with outcome `parked`, a terminal outcome (merge lane, Contracts and seams, "Lair pull request").
11. **A valid result is never timed out on a transient read.** Built by #608 and #610. A valid result file whose result checks or end reads fail only transiently, by a failed or incomplete read or `SNAPSHOT_ERROR`, is never ended `timed-out`. A later tick checks it again, and only that retry writes its outcome (strain launch, Components "Remediation strain launch", "A deferred write is not a budget overrun or an orphan"). The queue report names each such deferred result with its age.
    - A result head still absent after a fetch that completes, a ref fetch then `git cat-file -e` on the head, ends the run `invalid-result`. A fetch that fails is a transient read until the run's budget has passed, and then ends the run `invalid-result`.
    - A GitHub head that is still a strict ancestor of the result head once the run's budget has passed ends the run `invalid-result`. Before then it is a read not yet complete, as the merge lane states (Contracts and seams, "Lair pull request").

    The merge lane's rule that a result still unchecked when the budget passes ends the run `timed-out` (Contracts and seams, "Lair pull request", Result recording), and its #608 test of that rule, no longer apply.
12. **The merged exit closes the issue.** Built by #605. The merge lane's merged exit (Lifecycle "Exits") also closes the issue, as strain launch's "Assumptions about #631" require, since the pull request names no issue to close. The close is a write made before the exit marker, under item 8.
13. **The idle signal.** Built by #608, with #604's liveness hooks; #610 applies it to a remediation run. Claim integrity's idle signal ("Assumptions about #630", Idle signal) takes both of strain launch's stall rules (Failure modes "Stall"), the activity rule included: a session alive with no result whose last activity is more than 30 minutes old gives the idle signal. So when the `Stop` hook does not fire, the stall check still ends the run `stalled`; only when the activity hooks do not fire either does the budget check end it `timed-out`. Claim integrity's statement that with no `Stop` hook no idle signal comes no longer applies.
    - A remediation run's stall detection is the same idle signal with both stall rules, as for a delivery run. The merge lane's stall window measured from the start marker's `started_at` no longer applies wherever it appears: Components "Fix-up runs", "Budget, stall and crash"; Failure modes "Fix-up run lost in flight", its detection clause; Decided for you, "A fix-up run is supervised from its markers" and R15; Seam order, the #610 row; and Verification strategy, its #610 case "the stall window from `started_at`". That Failure modes row governs only the resulting state of a stalled remediation run.
14. **The decision digest.** Built by #611, after #608; #608 builds no digest wait. The digest's requirement is its row under State and ownership, under the ADR-0045 amendment of 2026-11-22 to decision 2. It extends [claim integrity](claim-integrity-design.md): `control/digest/` joins the `control/` list of its Lair state root, and its statement that the marker key is the one local item GitHub cannot give again reads as one of two, in all three places it is made: the marker key row of its State and ownership, the closing paragraph of that section, and its Decisions bullet on the marker key. The clean-up wait and every other extension of a part design land with #611:
    - #611 designs, during its build, the entry format and its escaping; the write's crash safety, by a temporary file and a rename or an equivalent; the write's place in the run-end write order and the clean-up wait; the recovery of an interrupted write; the marking of each entry `counted` or `unverified`, by whether its run's outcome marker counts, and the attribution of entries to sessions; how the queue report reports a failed write; the hygiene of temporary files; and the note of an `--admin` merge (merge lane, Contracts and seams, "Routing table", the row `MERGE=merged-admin`), written at the merged exit after the run's entry, with the note's crash safety, a stop between the merge call and the note included, and its place relative to the exit marker. The digest row's timing, before the run's clean-up, governs only the run's entry.
    - Any further override of a frozen part design this needs is recorded through a dated entry under Amendments here when #611's design settles it: of [strain launch](strain-launch-design.md)'s Lifecycle step 5, for the clean-up wait; of claim integrity's `control/` list, for the folder's mode and checks; of its Lifecycle, Start, for the folder's creation; of its statements of the one local item, its Decisions bullet on the marker key among them, beyond reading as one of two; and of its Contracts and seams, "Queue report". 15. **Re-claim refusals.** Built by #608 and #609. [Strain launch](strain-launch-design.md) runs a re-claim's start configuration, moved-head and superseded-design checks after the claim marker (Lifecycle step 1; Components "Start points"; Failure modes "Superseded design on a re-claim"). A refusal there leaves a claim with no strain, which claim integrity's crash rule ends `crashed` with stage `spawn`, counted, and the merge lane's row "Delivery `failed`" (Lifecycle "Run outcome to labels") gives a re-claim's `start_moved` end `lair:failed`, counted; strain launch gives both `lair:handoff`. So:
    - For a re-claim these three checks run before the claim marker, as admission checks, in claim integrity's claim sequence (Lifecycle) after step 3, so before the scan. They read the pre-image from the park marker of the claim whose counting outcome marker is the issue's latest, with outcome `parked` (item 1).
    - A refusal hands the claim attempt off as claim sequence step 4 hands off a suspect issue: after the re-read under invariant Write guards, a handoff marker carrying the attempt's nonce, then the `lair:handoff` label. Its `reason`, added to claim integrity's handoff reasons (Contracts and seams, "Marker payload, every kind"), is `branch-moved`, `start-config-changed` or `design-superseded`, for strain launch's `branch_moved`, `start_config_changed` and `design_superseded`, with `category` null. No claim marker is written, so no outcome is written and the breaker is unchanged.
    - A branch checked out in a kept worktree stays not claimed, with queue report reason `unpushed_work` and no new label.
    - A re-claim run that ends `failed` with cause `start_moved` takes `lair:handoff` in place of that row's `lair:failed`, a run-end handoff. Its run end writes the labels and pull request changes, then a handoff marker, then the outcome marker last (item 8). That handoff marker reuses the claim's nonce, carries reason `branch-moved` and adds no payload field.
    - For this design, the handoff clause of claim integrity's counting rule (Contracts and seams, "Counting rule") reads: a `handoff` marker carries the nonce of the claim attempt the handoff stopped, by a scan or by a re-claim refusal at admission, which no claim marker records; or, for a run-end handoff, the nonce of a counting `claim` marker on the same issue.     - Its pull request takes item 9's `lair:review` route, as a `failed` delivery run's pull request does when it passes item 9's checks: the issue gets `lair:handoff` and the pull request `lair:review`.
16. **Reason codes in the queue report.** Built by #608. Claim integrity's queue report prints a reason code that fails `^[a-z0-9][a-z0-9-]{0,63}$` as `unknown-reason` (Contracts and seams, "Queue report"; "Assumptions about #615", Reason codes). #615's codes are snake_case, some with a suffix, and so are strain launch's queue report reasons, so each would print as `unknown-reason`.     - Strain launch's reasons `unpushed_work`, `park_unanswered`, `too_many_decisions` and `decision_too_long` print from that closed list, under stage `admission` in claim integrity's issue line `issue <number>: <stage> <code>`.

## Trust boundaries

A user with write permission steers the Lair through these channels:

- the `readiness:ready` label on an unedited issue, as admission (ADR-0045 decision 10 and its 2026-11-21 amendment);
- `/lair answer` comments, as park answers (ADR-0045 decision 11);
- review comments on a Lair pull request, which reach its remediation strain through strain launch's author filter (Components "Remediation strain launch"), scanned before use; and the user's holds named in the [merge lane](merge-lane-design.md)'s Trust boundaries ("Residual: the Lair acts as the user's own login");
- the halt file on the user's own machine (ADR-0045 decision 17);
- the merge settings, only through the user's own settings files on the Lair's machine, as the [merge lane](merge-lane-design.md)'s Trust boundaries state (ADR-0045 decision 12);
- remote control on a Lair strain, as [strain launch](strain-launch-design.md)'s Trust boundaries state;
- the batch review of `lair:review` pull requests, and the decision digest as the veto channel (ADR-0045 decisions 12 and 14).

Two more channels reach the Lair from others:

- in-scope reviewer Bots (ADR-0043) and CI check descriptions reach a remediation strain's fix pass, through strain launch's author filter (Components "Remediation strain launch"), scanned before use;
- any commenter, a user without write permission included, can spend a pull request's one remediation strain or send it to `lair:review`, because the seed counts every author but the Lair's login; no comment text reaches a strain this way (strain launch, Components "Remediation strain launch", "The cost").

Strain containment follows strain launch, Trust boundaries, "Strain containment", with the containment of the key, the halt file and the Lair's tmux servers under Seams between the part designs, item 6, whose mechanism #646 designs. The markers, the key, the scanner session and the halt file follow [claim integrity](claim-integrity-design.md), Trust boundaries. The remaining risks are the [ADR-0045 residuals](../../adr/0045-lair-software-factory.md#residuals) and the residuals its amendments add.

## Lifecycle

Issue labels move as ADR-0045 decision 16 states:

- `readiness:ready` to `readiness:implementation` with `lair:claimed` at claim;
- to `readiness:done` when GitHub shows the pull request merged, and the issue is closed (Seams between the part designs, item 12);
- to `readiness:needs-decision` on an answerable park, keeping `lair:claimed` ([claim integrity](claim-integrity-design.md), Lifecycle, run end), a remediation run's park included (Seams between the part designs, item 10);
- `lair:handoff`, `lair:failed` and `lair:review` as each part design maps them:
  - every run end and exit: the [merge lane](merge-lane-design.md), Lifecycle "Run outcome to labels" and "Exits", with Seams between the part designs, items 2 (a `not-launched` remediation end's batch review) and 9 (the pull request of a delivery run that did not complete);
  - a suspect scan and an orphan: claim integrity, Lifecycle (claim sequence step 4) and Design invariants (Claim state);
  - a refused start or push, by start kind: [strain launch](strain-launch-design.md), Components "Start points", "Handling by start kind", with a re-claim's refusals and its `start_moved` end under Seams between the part designs, item 15: a handoff marker and `lair:handoff`, never `crashed` or `lair:failed`.

A run moves through these stages:

1. **Claim, spawn, run, result, labels, merge.** The tick admits an issue, writes the claim marker and labels, and spawns the strain (claim integrity, Lifecycle, claim sequence). The strain runs standard-delivery unattended and writes its result. The Lair records the run end: its label and pull request changes first, then the outcome marker last (the merge lane, Lifecycle "Run outcome to labels"; Seams between the part designs, items 1 and 8). It ends the session and cleans up as strain launch's Lifecycle steps 4 and 5 state, under Seams between the part designs, item 7. The merge lane then works the pull request (the merge lane, Components "Merge-lane step of the tick").
2. **Park, answer, re-admit, continue.** A parked result becomes its label moves, then the park marker, then the outcome marker last (Seams between the part designs, item 8). The user answers and relabels `readiness:ready`. Admission runs again, the readiness check and the re-claim checks of Seams between the part designs, item 15, included. The new strain starts on the pushed branch with the answers as settled decisions.
3. **Post-PR remediation.** A Lair pull request gets at most one remediation run, under Seams between the part designs, item 2. Its dispatch and launch follow strain launch, Components "Remediation strain launch", and its markers and route follow the merge lane, Lifecycle "Stage 3: post-PR fix-up", under Seams between the part designs, items 8 and 10.
4. **Halt and circuit breaker.** The halt file and the breaker follow claim integrity, Lifecycle, with the outcomes of Seams between the part designs, item 4. Their effect on remediation runs and merges follows the merge lane, Lifecycle "Stage 4: halt and circuit breaker".
5. **Start-up sweep.** The start-up sweep and the removal of orphaned sessions and worktrees follow Seams between the part designs, item 7.

## Verification strategy
