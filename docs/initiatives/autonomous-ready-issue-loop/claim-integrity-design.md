# Solution design: Lair claim integrity

This is the claim-integrity design for the Lair, issue #632, split from the [solution design](solution-design.md) of epic #603 after its round-3 review. It links the [PRD](../../prds/autonomous-ready-issue-loop.md), [ADR-0045](../../adr/0045-lair-software-factory.md) and the [solution design](solution-design.md) rather than restating them, and cites ADR-0045 as "ADR-0045 decision N". It follows the user's answers of 2026-11-21, four given before design review round 1 and two given after it, and the user's two answers of 2026-11-22, given after round 2. Its read rule and circuit breaker follow the user's answer of 2026-11-22 after round 4, recorded in the [review record](claim-integrity-review-record.md): no fixed read budget, and a breaker recomputed from GitHub markers each tick, as ADR-0045 decision 17 states.

For its scope, this design supersedes these parts of the solution design:

- in the component Controller tick and admission: the claim, the readiness-check call, the injection scan, labels and marker comments, the halt switch, the wall-clock budget, the start-up sweep, the lock and the queue report;
- in the component Strain result and liveness, the sentence "Crash and stall detection follow ADR-0045 decision 5", whose rules this design states;
- the marker side of Park answer round trip, and the marker side of Decision digest and circuit breaker, its sentence "so a restart by the user re-arms the Lair" included;
- the Contracts Claim marker comment, Park marker comment, Readiness-check call at claim and Queue report;
- the claim-marker, park-marker, halt-file, single-instance-lock and local-cache rows of State and ownership;
- in Lifecycle: the label move to `readiness:needs-decision` "with `lair:claimed` removed", the outcome recorded in the claim marker in stage 1, and the start-up sweep of stage 5, which reached every `readiness:implementation` issue and ran only at start;
- the Crash, Stall, GitHub API failure, Lock already held, Orphaned claim and Stale design rows of Failure modes, its row on the `Stop` hook not firing while a workflow runs in the background, and the wall-clock part of its Budget overrun row;
- the Decisions on the queue report contents, the outcome in the claim marker and the circuit-breaker scope, and the stall part of the decision on the stall and exit fallbacks.

Every other part of the solution design stands. Strain launch and containment belong to #630, the live launch probes to #604, the merge lane to #631, and the readiness check to #615; this design states each assumption it makes about them under Contracts and seams.

## Context and code truth

This design builds on the following code, as it stands on trunk:

It keeps brood state in `.hivemind/broods/<brood-id>/` of the coordinator checkout. When it has written a plugin-folder `Read` rule it launches with `--settings ../../../../.hivemind/broods/<brood-id>/strain-settings.json`, a file holding only those rules; when it has none it launches with no `--settings` flag. The script also copies the coordinator's `.claude/settings.local.json` into each worktree, and [ADR-0010](../../adr/0010-permission-allowlist-posture.md) records that since Claude Code 2.1.211 a worktree session reads the main checkout's local settings file anyway. Its `submit_strain` loads the strain's `.hivemind/brood/task.md`, which holds the issue-derived description after a control-byte strip, into a tmux buffer and pastes it into the strain's pane. - [ADR-0032](../../adr/0032-defer-marker-sentinel-and-agent-layer-home-truth.md) recognizes the defer marker only when a self-authored body starts with an exact HTML-comment sentinel, compared at byte 0, never by a pattern. `plugin/skills/github-review-loop/scripts/fix-history-classify.jq` reads `lastEditedAt` the same way.

## Components

### Design invariants

Each invariant below is stated once, here. Every later section cites it by name, as "invariant Claim state", and never restates it.

- **Claim state.**
  - The Lair issue list is the open issues labeled `lair:claimed`, `lair:review`, `lair:handoff`, `lair:failed`, `readiness:ready` or `readiness:implementation`. A Lair issue is an issue on that list that carries a `lair:*` label, a counting claim marker or a counting handoff marker (the user's 2026-11-21 sweep answer). A markerless Lair issue is one with no counting claim marker.
  - An open claim is a counting claim marker with no counting outcome marker of its nonce.
  - A run is one strain run under a claim: the claim's own run, whose run id is the claim nonce, or a remediation run of the claim's pull request (#610), whose run id is its own 32 lowercase hex digits from `/dev/urandom`. Outcome markers, result files and result consumption key on the run id. Of the counting outcome markers of one nonce, the one with the latest `ended_at`, and of equal `ended_at` values the later comment, decides the issue's labels.
  - A live strain is a strain session for a run of the nonce, or, for a markerless Lair issue, any strain session for the issue; or an unconsumed result file, one whose run id has no counting outcome marker yet.
  - A pull request of the issue is a pull request, by any author, open or merged, that GitHub links to the issue as closing it. This is the PRD's "no pull request" (Budgets and recovery).
  - A crashed claim is an open claim with no live strain, whatever the pull requests of the issue: its strain session is gone, or never started, and no result file of it is unconsumed (ADR-0045 decision 5: an exit with no result is a crash). It gets an outcome marker `crashed`, then the `crashed` labels.
  - An orphan is a markerless Lair issue in `readiness:implementation` with no live strain and no pull request of the issue, that carries no counting handoff marker and no `lair:handoff` label. This is ADR-0045 decision 17's sweep rule, and it keeps that rule's "no pull request". An orphan gets labels only: `lair:failed` added, `readiness:implementation` and `readiness:ready` removed. A handed-off issue a person moved to `readiness:implementation` by hand is never an orphan.
  - A Lair issue whose counting claim markers are all closed is neither a crashed claim nor an orphan; its labels follow invariant Markers and labels. A crashed claim or an orphan is marked failed and never returned to ready.
  - The reconciler never touches a non-Lair issue.
  - The crash rule reads the verifier's results, the strain-session lookup and the result files; the orphan rule also reads the Lair issue list and the issue's linked pull requests. When one of them is unavailable, that tick gives no crash or orphan verdict it would decide, under invariant Unavailable reads.
- **Markers and labels.**
  - Counting markers decide which claim and which outcome exist; labels follow them.
  - Each label pairs with a marker, except the `lair:failed` a markerless orphan gets under invariant Claim state: `lair:claimed` with a counting claim marker; `lair:handoff` with a counting handoff marker, or with the counting park marker of an `approval` park or a third park; `lair:failed` and `lair:review` with a counting outcome marker under #631's mapping.
  - The reconciler moves labels forward only. It skips the repair of an outcome marker's labels when a `readiness:ready` labeled event whose actor has write permission is newer than the latest counting outcome marker: the Lair never applies `readiness:ready` (ADR-0045 decision 10), so that event is the user's re-admission (ADR-0045 decision 11), and admission decides what happens next. Admission applies the same rule from its side: it claims an issue only when its admitting event is newer than the issue's latest counting outcome marker, so a failed issue whose label writes failed is not claimed again until the user re-admits it. Re-adding a label an issue already carries makes no labeled event, so to re-admit an issue that still carries `readiness:ready`, the user removes that label and applies it again. Newer means a later GitHub `createdAt` than the marker comment's; an equal time is not newer.
  - A handed-off issue is never re-admitted: a suspect issue is handed off and never run (ADR-0045 decision 10). Admission never claims an issue with a counting handoff marker, whatever its labels and label events, removing and applying `readiness:ready` again included. The reconciler always repairs the `lair:handoff` of a counting handoff marker, and the Lair never removes that label. The user handles a handed-off issue outside the factory.
  - Of the labels, only `lair:claimed` without a counting claim marker trips the halt `marker-missing`. Any other `lair:*` label without its marker is left alone and never claimed.
- **Lock scope.**
  - One controller runs per lock scope. A lock scope is one repository (the state root, keyed by the repository's GraphQL node id), one user account (the home directory in the password database) and one machine.
  - Creating the state root, `control/` and `control/lock` are the only writes before the lock is held, and all three are idempotent.
  - The Lair takes a non-blocking `flock` on `control/lock` before any other write and holds it for its whole life. Each tick it checks that the path `control/lock` still names the file it holds locked; when it does not, the Lair writes nothing more and exits non-zero with `lock lost`.
  - The lock descriptor is never inherited. Every child the controller launches (tmux, strains, remediation strains, scanner sessions, helper scripts) starts with it closed, so a strain that outlives a crashed controller never holds the lock, and the kernel frees the lock when the controller exits.
  - The lock covers the Lair's own GitHub writes, launches, key creation and halt-file writes. It does not cover the user's edits, triage, interactive sessions, the user's halt-file writes or deletion, or any other lock scope.
  - Outside one lock scope, exclusivity is detect-and-halt by markers and labels, never prevention. Two Lairs on one repository may both claim an issue and may fail each other's claims as orphans; that setup is unsupported.
  - The re-take of the claim inputs before the claim marker narrows an edit race. It is not mutual exclusion.
- **Lair-written text.**
  - Every string the Lair writes to GitHub, a terminal, a tmux pane or a scanner prompt is a fixed template, a token matching a validated pattern, or the one bounded slot.
  - The patterns: a `kid` is `^[0-9a-f]{16}$`; a nonce, session id, run id or scan id is `^[0-9a-f]{32}$`; a GitHub node id is `^[A-Za-z0-9_=-]{1,128}$`, the charset of `assert_node_id`; the state root path is `^/[A-Za-z0-9._/-]+$`, the charset of `hivemind_assert_identifier`, so it holds no glob character for a `Read(//...)` or `Edit(//...)` rule. A value that fails its pattern is never written: a `kid` that fails its pattern prints as `malformed`, and a state root path that fails refuses start (Lifecycle).
  - The slot is the park marker's question block: strain-authored data (question, options, recommendation), at most 2000 bytes, holding only characters of the Unicode general categories L, M, N, P and S, the ASCII space and LF. Any other character rejects the park record: control and format characters (U+200B and U+2066 to U+2069 among them), separators other than the space and LF, private-use and unassigned code points.
  - The Lair writes the slot inside a fenced code block whose backtick fence is one backtick longer than the longest backtick run in the slot, and at least three long, so no line of the slot can close it (CommonMark 0.31.2, section 4.5, fenced code blocks). A mention or a link in the slot shows as code.
  - No Lair reader reads the slot's bytes; only a GitHub reader sees them. The Lair never prints them, and never puts them in a scanner prompt or a signed payload.
  - Beyond the fields every marker carries, the signed park payload carries only `key` (pattern `^[a-z0-9][a-z0-9-]{0,63}$`) and `type`.
  - A park record that breaks this rule is never posted; its handling is #631's result check.
  - Claim, outcome and handoff marker text and the queue report have no slot.
  - The strain's own task text is #630's, under the assumption that the captured text reaches the strain only as a file (Assumptions about #630).
- **Unavailable reads.**
  - Every read the controller makes returns a value or `unavailable`. A read is unavailable when its call fails, is rate-limited, a secondary rate limit included, or times out, when `hivemind_graphql_response_check` rejects its response, when a page of a connection in it cannot be read, or when a file or directory cannot be read, created or written where the step needs it.
  - Every connection is read page by page to its end. A connection longer than 10 pages of 100 nodes is the value `too-large`, never `unavailable`.
  - Absence is a value only where the read's own contract says so: for the halt read, no entry is `clear`.
  - A guard is the condition a write, halt or verdict waits on, as these invariants, Contracts and seams and Lifecycle state it. The reads a guard uses are the reads its own definition names, the probe of each file or directory it writes included.
  - A guard that uses an unavailable read does not fire, and neither does its negation: no write, halt cause, `marker-invalid` verdict, failed-check fingerprint, crash verdict or orphan verdict follows from it. A decision's writes begin only after every read of its guards returned a value.
  - Availability is never stored, so the next tick reads again with no re-arm. The queue report's `claims:` lines give only the reasons, an unavailable read among them, that blocked the current tick's claim step (Queue report).
  - The controller reaches GitHub, the trunk fetch, tmux and the state root only through one read-and-write library, built by #605, that records each read. Reads another slice adds (#608, #609, #610, #631) follow the same rule.
- **Write guards.**
  - A tick stage computes from the reads the tick took for it, the shared read of tick steps 1 to 3 among them (Lifecycle). Immediately before each GitHub write the stage makes, the Lair reads again, through the read library, every mutable field that write's guard uses. These are the GitHub fields: the issue's labels, its timeline events (the `readiness:ready` labeled events with their actors and those actors' write permission among them), its marker candidates through the verifier, and, for the orphan rule, its linked pull requests. They are also the local liveness state: the strain-session lookup, the run's result file and whether it is unconsumed, and #630's idle signal.
  - The liveness sites: a `crashed` outcome marker re-reads that the strain session is still gone and that no result file is unconsumed; an orphan's label writes re-read that no live strain exists; a `stalled` outcome marker re-reads the idle signal, the strain session and that no result file exists; a `timed-out` outcome marker re-reads the strain session and that no result file exists.
  - When a field differs from the value the stage computed from, apart from the stage's own earlier writes in the same sequence, the write is skipped. When the re-read is unavailable or `too-large`, the write is skipped too (invariant Unavailable reads). The next tick decides afresh from a new read. A run whose run-check write a `too-large` read skips is still ended at its budget or on its idle signal, with no outcome marker (Lifecycle, run checks).
  - A skipped write stops its sequence as a failed write does, and the next tick moves the partial state forward (Failure modes).
  - A write whose guard uses no read field, only the proof of success of the write before it, re-reads nothing: claim step 7's label writes after the claim marker, and the `lair:handoff` label after the handoff marker. The claim marker's re-read is the re-take of claim step 5, and the handoff marker's is the re-take of the claim-relevant fields in claim step 4 (Lifecycle).
  - Writes another slice adds to a tick stage (#609, #610, #631) follow the same rule. Halt-file writes are local, not GitHub writes; Halt file under Contracts and seams governs them.
  - The re-read narrows a race with the user's edits. Like the re-take, it is not mutual exclusion.

### Lair state root

One directory per repository, outside every checkout and worktree: `<home>/.local/state/hivemind/lair/<repo-key>/`. `<home>` is the user's home directory in the password database, read through bash's `~<user>` expansion with `<user>` from `id -un`; the Lair never reads `HOME` or `XDG_STATE_HOME`, so no environment value moves the lock scope. `<repo-key>` is the first 32 hex digits of the SHA-256 of the repository's GraphQL node id. The path matches the state-root pattern of invariant Lair-written text, or Start refuses. Start checks with `lstat` that the state root and `control/` are directories, not symlinks, owned by the user, with mode 0700. The state root, `control/` and `control/lock` are the pre-lock writes of invariant Lock scope, made by Start under Lifecycle. Every exclusive create, every open with `O_NOFOLLOW` or `O_APPEND`, and every flush to disk under the state root is made by `perl`, with `sysopen` and its `Fcntl` flags and with `IO::Handle`'s `sync`, since bash cannot open a file with `O_NOFOLLOW` or `O_NONBLOCK` nor flush one to disk, and its `noclobber` create opens an existing FIFO. Each such write calls `syswrite` again on the bytes not yet written until every byte is written; a `syswrite` that fails or writes no byte is a write failure, handled as a write error. The Lair prints the path on start, under invariant Lair-written text. It holds:

- `control/`, mode 0700, the contained directory: `lock`, the single-instance lock file; `marker.key` (mode 0600); `marker.key.new`, the key's temporary name, present only while a key is created; the halt file `halt`; `write-check`, present only during Start's write check; `scan.sock`, the socket of the scanner's private tmux server; and `cache/`, which holds only the last queue report;
- `scan/`, mode 0700: `cwd/`, the scanner's empty start directory, and `<scan-id>/`, one directory per scan.

### Single-instance lock

The controller opens `control/lock` on one descriptor and takes an exclusive `flock` on it. When it is taken, how long it is held, its scope, its coverage, the per-tick path check and the rule that no child holds it are stated in invariant Lock scope.

### Marker signer and verifier

The Lair writes four marker kinds as issue comments: claim, outcome, park and handoff. Each carries a claim nonce and a signature made with `marker.key`, a 32-byte random key the Lair creates at Start (Lifecycle). #605 builds the primitive, key loading, the key file checks and the verifier; #608 builds key creation, inside Start.

- **Primitive.** The signature is HMAC-SHA256 (RFC 2104), built by the RFC's construction from the SHA-256 tool Start found. Start checks the signer against an HMAC-SHA256 test vector of RFC 4231 and refuses start on a mismatch.
- **Key handling.** The key file's bytes reach the controller only through a file descriptor read by `od`, into an unexported shell variable, once, at Start. The padded key blocks reach the SHA-256 tool only on its standard input. No key byte is ever on a command line, in an environment, or in a file other than `marker.key` and, while a key is created, `control/marker.key.new`. That pipe and the controller's memory are kept from strains and remediation strains by #630's PID-isolating sandbox (Assumptions about #630), and from the scanner session by its own settings, which limit it to its own scan files; where the platform offers no such sandbox, they are the proposed process-reach residual under Changes to shared documents.
- **Key file checks.** Every read of `marker.key` checks that it is a regular file, not a symlink, owned by the user, with mode 0600, one link and exactly 32 bytes. Any other state is `key-invalid`, which refuses start.
- **Key creation.** Start writes 32 bytes from `/dev/urandom` to the fixed temporary name `control/marker.key.new`, created exclusively with mode 0600, flushes it to disk, then links it to `marker.key` with a link that never replaces an existing entry, and removes the temporary name.
- **Leftover temporary.** Before any key read, Start removes a leftover `control/marker.key.new`. It must be a regular file, not a symlink, owned by the user, with mode 0600 and one link, or two links when `marker.key` names the same file; any other state refuses start with `key-invalid`. A crash before or after the link step therefore leaves, once Start runs again, the key in `marker.key` alone or no key at all.
- **Key reset.** The user deletes `control/marker.key`, then starts the Lair with `--retire-kid` (Lifecycle). With the one-link check and the leftover removal, no link to the old key stays under `control/`.

Every Lair reader of a marker goes through one verifier, which applies the counting rule under Contracts and seams and returns one of its results. This answers B3-3.

### Readiness snapshot

For each candidate the Lair takes one snapshot: one paged GraphQL read of the issue node, with the tick's trunk commit. Admission, the readiness check and the captured text come only from the claim inputs, defined under Snapshot in Contracts and seams. The claim pins the snapshot's trunk commit, and the strain starts there. This answers B3-16.

### Scanner session

The pre-spawn injection scan of ADR-0045 decision 10 runs in a locked-down scanner session: an interactive `claude` session in `dontAsk` permission mode, on the Lair's private tmux server, started in an empty folder outside every repository, loading only the hivemind plugin, no hooks and no settings but the Lair's own file. Its rules let it read its input and its verdict line and edit only that line; explicit deny rules remove every other tool that runs commands, writes, fetches or delegates. A fixed prompt is the adapter between the scan files and `hivemind:injection-scan`, whose `items` input and `results` output stay as they are (Scanner prompt under Contracts and seams). The Lair accepts only the exact clean token. ADR-0045 decision 10 keeps its text. This answers B3-1.

### Claim sequence

The ordered reads and writes that take a candidate from snapshot to spawned strain, given under Lifecycle. Every write follows the one before it only on positive proof of success. This answers B3-10.

### Reconciler and start-up sweep

The reconciler applies invariants Claim state and Markers and labels each tick, as ADR-0045 decision 2's per-tick reconcile. Its first run in a session is the start-up sweep of ADR-0045 decision 17 for claims. Its place in the tick and its other rules are under Lifecycle.

### Halt file and circuit breaker

The halt file stops new claims (ADR-0045 decision 17). The circuit breaker counts the runs this Lair session launched and ended, recomputed each tick from their signed outcome markers on GitHub, read newest first until it has the 3 most recent counted runs (ADR-0045 decision 17). A trip, and each tripwire, writes its own cause to the halt file on disk at once: by exclusive create when no entry exists, else by appending to the entry, the user's own included. Every halt is so durable, and only the user deleting that file re-arms the Lair. Only a halt whose write fails is held in memory, and Start refuses while `control/` cannot be written. The tripwires and the `stalled` outcomes the breaker counts extend ADR-0045 decision 17 through the proposed 2026-11-22 amendment under Changes to shared documents; the non-counting outcomes the breaker counts, its window rule, the append and Start's refusal are decided for the user (Decisions).

### Queue report

A report of the Ready Issue queue, under invariant Lair-written text, that gives the cause of each failure. This answers B3-19.

## State and ownership

GitHub alone is authoritative (ADR-0045 decision 2). These rows replace the solution design's claim-marker, park-marker, halt-file, single-instance-lock and local-cache rows. Every other row stands.

| State | Writer | Readers | Authoritative |
| --- | --- | --- | --- |
| Claim marker comment | Lair, at claim; never edited | Lair verifier (admission, reconciler, budget, breaker, merge lane under #631), user | yes, when it counts |
| Outcome marker comment | Lair, at run end or when the reconciler ends a claim; never edited | Lair verifier (reconciler, circuit breaker, digest), user | yes, when it counts |
| Park marker comment | Lair, from the strain's park record; never edited | Lair verifier (answer admission, park count), user | yes, when it counts |
| Handoff marker comment | Lair, on a scan handoff; never edited | Lair verifier, user | yes, when it counts |
| `lair:claimed` label | Lair | Lair, triage, user | no; it pairs with a counting claim marker under invariant Markers and labels |
| Marker key `control/marker.key` | Lair, at Start: on first start, or on the start after the user's key reset | Lair signer and verifier only, from memory after Start | no; a secret, and the one local item that cannot be rebuilt from GitHub, under the proposed amendment to ADR-0045 decision 2 |
| Halt file `control/halt` | User; or the Lair's breaker and tripwires, by exclusive create when no entry exists, else by appending one record, never by an overwrite or truncation; removed only by the user | Lair, each tick | no; a control input (ADR-0045 decision 17) |
| Lock `control/lock` | Lair | Lair | no; process exclusion within one lock scope under invariant Lock scope |
| Scanner tmux socket `control/scan.sock` | Lair, through tmux | Lair | no; process plumbing, removed at Start |
| Scan files `scan/` | Lair writes the input, the settings and the verdict placeholder; the scanner session edits the verdict line | Scanner session reads the input and the verdict; Lair reads the verdict | no; each scan directory is removed after its scan, and every one at Start |
| Queue report `control/cache/queue-report.txt` | Lair | User | no; rebuilt from GitHub each tick, and never read back by the Lair |
| Session records, in memory | Lair | Lair | no; they end with the session, and a new session starts them empty, as the breaker and wall-clock budget rules require |

The session records are the session id, the runs this session launched, by run id, with their issue numbers, their claim or launch times, the tick count at each claim or launch, and the end time of each run this session ended (the `ended_at` the Lair wrote in its outcome marker or read from it, or, for a run it ended with no outcome marker, the time it ended the run's session), the spawns made, by run id, the opening time of the breaker's window, the failed-check fingerprints, the re-take abort counts, the last issue the readiness check checked, the causes written to the current halt entry, and the halts held in memory. They hold no outcome: the breaker reads outcomes from GitHub each tick. They live only in the controller's memory and are never written to a file. No local item but the key holds anything GitHub cannot give again: a deleted marker comment is caught by the `lair:claimed` rule of invariant Markers and labels, or fails toward stopping under Reader failure direction. The reads of every row, the probe before each write included, follow invariant Unavailable reads.

## Contracts and seams

Fields and seams only. Each slice builds the code.

- **Marker comment.** The body's first line is exactly `<!-- lair-marker-v1 <payload> <sig> -->`, then LF, then readable text. `<payload>` is unpadded base64url (`[A-Za-z0-9_-]`, at most 4096 bytes) of a compact JSON object, decoded by mapping `-` and `_` to `+` and `/`, padding with `=`, and running `base64` with the decode flag Start found. `<sig>` is the lowercase hex HMAC-SHA256, under `marker.key`, of the payload's bytes as written. The readable text follows invariant Lair-written text. No Lair reader reads it.
- **Marker payload, every kind.** `v` (1), `kind` (`claim`, `outcome`, `park` or `handoff`), `repo` (the repository's GraphQL node id), `issue` (number), `nonce` (one per claim attempt), `session` (the Lair session id), `kid` (the first 16 lowercase hex digits of the SHA-256 of the key) and `at` (UTC time, in the form `YYYY-MM-DDTHH:MM:SSZ`). The nonce, the session id, every run id and every scan id are 32 lowercase hex digits from `/dev/urandom`.
  - `claim` adds `admit_event` (the node id of the admitting labeled event), `body_sha256`, `trunk` (the snapshot commit) and `scan` (the scan id).
  - `outcome` adds `run` (the run id, under invariant Claim state), `outcome` (`complete`, `parked`, `blocked`, `failed`, `stalled`, `timed-out` or `crashed`), `ended_at` (UTC time, in the form of `at`), `pr` (number or null) and, for `crashed`, `stage` (`claim-labels`, `spawn` or `run`).
  - `park` adds `key` and `type` from the park record, under invariant Lair-written text.
  - `handoff` adds `reason` (`scan-suspect` or `scan-malformed`) and `category` (`P1` to `P4`, or null).
- **Counting rule.** A comment is a marker candidate when the Lair's login wrote it and its body starts, at byte 0, with `<!-- lair-marker-`. The Lair's login is `viewer { login }`, read once at Start. A candidate whose first line matches the form above and whose payload decodes with `v` 1 and a `kid` other than the current key's id is foreign: it does not count, it is not invalid, and it halts nothing. Any other candidate counts only when all hold:
  - its author is the Lair's login and `viewerDidAuthor` is true;
  - it is unedited: its `lastEditedAt` key is present and null;
  - its first line matches the form above exactly, CR bytes included, and its payload is at most 4096 bytes;
  - its payload decodes, with `v` 1, `kid` equal to the current key's id, `repo` and `issue` equal to the issue being read, and `at`, and an outcome marker's `ended_at`, in the UTC form above;
  - its signature verifies under the current key;
  - it carries a claim nonce: a `claim` marker carries its own; an `outcome` or `park` marker carries the nonce of a counting `claim` marker on the same issue; a `handoff` marker carries 32 lowercase hex digits, the nonce generated for the claim attempt its scan stopped, which no claim marker records and which the signature binds.

  A candidate that fails any check is invalid. A comment by any other login is never a candidate, whatever it holds. Identical counting markers count once. For each candidate the verifier returns `counts`, `foreign`, `invalid`, `unavailable` when a page of the issue's comments is unavailable (invariant Unavailable reads), or `too-large` when the issue's comments are longer than 10 pages of 100; a check it cannot run never makes a candidate invalid.
- **Reader failure direction.** Every marker reader fails toward stopping. In the rules below, "does not count" means the verifier read every comment and returned `foreign` or `invalid`, or found no counting marker. An `unavailable` or `too-large` result skips the reader for that tick and never writes an outcome marker, counts as a breaker failure, lists as `unverified`, halts as `marker-invalid` or `marker-missing`, or refuses a park answer for good; an `unavailable` result never ends a strain; `too-large` on a Lair issue halts with cause `too-large`, and the run checks end a session this Lair session launched for it at its budget or on its idle signal, with no marker (Lifecycle):
  - any `invalid` candidate, on any issue the Lair reads, writes the halt file with cause `marker-invalid`, and the issue is not claimed;
  - the `lair:claimed` case of invariant Markers and labels writes the halt file with cause `marker-missing`;
  - a run whose claim marker does not count gets no outcome marker from run end, the budget check or the stall check, since the verifier would find that outcome marker invalid. The budget check ends, at its budget and with no marker, a session this Lair session launched for it, and leaves every other session alone. The Lair ends only a session it launched: one of a run this session holds in memory, or one for a run of a counting claim marker's nonce. A markerless issue's sessions, the user's own brood strains among them, are never ended. The issue's `lair:claimed` halts the Lair with cause `marker-missing`;
  - the breaker counts as a failure a run this session ended whose outcome marker does not count;
  - an answer to a park whose marker does not count is never admitted (#609);
  - the digest lists as `unverified` a run whose outcome marker does not count (#611).
- **`body_sha256`.** Lowercase hex SHA-256 of the ASCII string `v1:<T>:<B>`, where `<T>` is the hex SHA-256 of the title's bytes and `<B>` the hex SHA-256 of the body's bytes, both exactly as the GraphQL read returns them, extracted with `jq -j '.title // ""'` and `jq -j '.body // ""'`. A null body and an empty body both hash as zero bytes. CR bytes, CRLF line endings, trailing newlines and Unicode forms are kept as read, with no normalization. Each hash is computed from a pipe, never through command substitution, which drops trailing newlines. The field keeps its name although it covers the title too. This answers B3-18.
- **Snapshot.** One paged GraphQL read of the issue: `number`, `state`, `title`, `body`, `lastEditedAt`, the issue type, labels, the `LABELED_EVENT`, `UNLABELED_EVENT` and `RENAMED_TITLE_EVENT` timeline items with actors and times, `blockedBy` numbers and states, the parent's number, state, issue type, labels, title and body, the sub-issue count, and every comment with the fields the counting rule needs and its `createdAt`, paged to the end. A connection longer than 10 pages of 100 nodes makes the snapshot `too-large`; a read `hivemind_graphql_response_check` rejects, or a page that cannot be read, is a snapshot error. The write permission of the admitting label's actor is one REST read in the same evaluation. This field list is the one definition of the snapshot, and it holds every GitHub input of #615's readiness check (Assumptions about #615). `updatedAt` is not read.
  - The claim-relevant fields are every snapshot field except the comments, of which only the Lair-login marker candidates are claim-relevant. A comment by any other login, or an edit of one, changes no claim input.
  - The claim inputs are the claim-relevant fields, the admitting actor's write permission, the tick's trunk commit and the halt read. Admission, the readiness-check call, the captured text and `body_sha256` are functions of the claim inputs only.
  - The tick guards of a claim are the lock path check (invariant Lock scope), the halts held in memory, the breaker, the lane read (no open non-draft Lair pull request, ADR-0045 decision 12, through #631's lookup) and the live-strain read for the issue. A claim writes only when every claim input and every tick guard, taken again before the claim marker, equals its first take. This re-take is the claim marker's re-read under invariant Write guards. The trunk commit is not fetched again: the claim pins it.
- **Unedited since the admitting event.** The title and body are unedited since the admitting labeled event when `lastEditedAt` is null or earlier than the event's time, and no `RENAMED_TITLE_EVENT` is at or after it. A `lastEditedAt` equal to the event's time counts as edited, since both have one-second granularity.
- **Readiness-check call at claim.** The Lair calls the check with the snapshot and the trunk commit, never letting it read GitHub itself. The result is the one the [idea-to-ready PRD](../../prds/idea-to-ready.md) names under "Readiness check output": track, pass or fail, and reason codes. Only a pass is claimed. The check runs under the timeout tool Start found. A non-zero exit, a malformed result, or no result within 60 seconds is the Lair-side state `check-error`, never a pass. Per tick the Lair checks at most 5 candidates, in ascending issue number, starting after the last issue it checked in the tick before and wrapping, so an issue that keeps erroring never starves the others. A candidate whose fingerprint, the SHA-256 of its claim-relevant fields and the trunk commit, equals that of its last failed check this session is not checked again; its cached reasons are reported.
- **Scanner launch.** The Lair starts the scanner with `tmux -S <state root>/control/scan.sock new-session -d -c <state root>/scan/cwd`, running `claude --permission-mode dontAsk --setting-sources project --settings <state root>/scan/<scan-id>/settings.json --plugin-dir <hivemind plugin root> --strict-mcp-config`. `scan/cwd/` is empty and lies outside every repository, so no project or local settings file loads, no user settings file loads, no plugin but hivemind loads, and no MCP server starts. The Lair closes the lock descriptor in the child.
- **Scanner session settings.** Written by the Lair per scan to `scan/<scan-id>/settings.json`:
  - `permissions.allow`: `Read(//<state root>/scan/<scan-id>/input.txt)`, `Read(//<state root>/scan/<scan-id>/verdict)`, `Edit(//<state root>/scan/<scan-id>/verdict)`, `Skill(hivemind:injection-scan)` and the hivemind plugin-folder `Read` rule. The `Edit` rule is the only write rule.
  - `permissions.deny`: `Bash`, `Write`, `NotebookEdit`, `WebFetch`, `WebSearch`, `Task`, `Agent` and `mcp__*`.
  - `disableAllHooks`: true, so no plugin hook runs in the scanner and no capture hook stores the scanned text.
- **Scanner prompt.** The Lair pastes one fixed template, under invariant Lair-written text, holding only the scan id and the two paths derived from it. It is the adapter to `hivemind:injection-scan`, whose contract is unchanged: the skill takes `items` (`item_ref`, `body`) and returns its `results` YAML to the calling session, with no step that reads or writes a file. The template tells the session, in order:
  1. read `input.txt`;
  2. invoke `hivemind:injection-scan` with one item: `item_ref` the scan id, `body` the file's whole content;
  3. map the one `results` entry by this fixed table: `verdict: clean` gives `clean`; `verdict: injection-suspect` with `pattern_category` `P1`, `P2`, `P3` or `P4` gives `injection-suspect` and that category, after one space;
  4. edit `verdict`, replacing `pending` with the mapped text and changing nothing else.

  The session's model applies the table, so the mapping is a filter, not a boundary (Trust boundaries). The Lair's reading of the verdict file is deterministic: a result the table does not cover, or any `field_excerpt` or `reason` text in the line, makes the verdict malformed, handled as suspect.
- **Scan input.** `input.txt` holds the title and body bytes that `body_sha256` covers: the title bytes, one LF, then the body bytes, each extracted as `body_sha256` extracts it.
- **Verdict file.** Before the launch the Lair writes `verdict` as `lair-scan-v1 <scan-id> pending` LF. The scanner replaces `pending` with its verdict. The Lair reads the file bounded to 129 bytes:
  - `lair-scan-v1 <scan-id> clean`, with or without one trailing LF, is the clean token, and the only verdict the Lair accepts;
  - `lair-scan-v1 <scan-id> injection-suspect <P1|P2|P3|P4>`, with or without one trailing LF, is suspect;
  - any other content, a stale scan id included, is malformed and handled as suspect;
  - the placeholder still in place after 300 seconds, or a missing file, is a scan error.

  The Lair takes a verdict only when two reads 2 seconds apart return equal bytes other than the placeholder. It then ends the scanner session, reads the file a last time, takes that read as the verdict, and removes the scan directory, whatever the verdict.
- **Halt file.** Its path is `control/halt` under the state root. The halt read is an `lstat` of that path: no entry is clear, and any entry halts. A regular file is read bounded to 4096 bytes; any other entry type, a directory, symlink or FIFO included, halts with cause `user` and is never opened. An unreadable `control/` makes the halt read unavailable (invariant Unavailable reads).
  - The Lair writes each halt as one record: `cause: <code>` LF, `at: <UTC time>` LF, then for `breaker` one `run: <issue> <outcome>` line per counted run, and for `marker-invalid`, `marker-missing` and `too-large` one `issue: <number>` line, with a `comment: <node id>` line for `marker-invalid`, the node id matching its pattern under invariant Lair-written text.
  - When the halt read finds no entry, the Lair creates the file by exclusive create, holding `halt` LF then the record, in one write, continued under Lair state root when `syswrite` writes only part of it. When an entry exists, the user's or an earlier cause's, or the exclusive create fails because one has appeared, the Lair appends the record in one write, continued the same way, on a descriptor opened with `O_WRONLY`, `O_APPEND`, `O_NOFOLLOW` and `O_NONBLOCK`, with neither `O_CREAT` nor `O_TRUNC`, once `fstat` on it shows a regular file owned by the user. It never overwrites, truncates or deletes the file.
  - The Lair writes each cause at most once to one entry in a session: it keeps in memory the causes it wrote since a halt read last found no entry.
  - The file's cause is its first record's when the file starts with `halt` LF then a record of the form above, so the first cause is whichever came first. Any other file reads as cause `user`, a user's file with Lair records appended included.
  - A halt whose write is not made, because the halt read is unavailable or the create or append fails, is held in memory (Lifecycle).
  - Cause codes and the user's action before deleting the file, which the user takes for every record the file holds, after reading them all: `breaker`, find and fix the shared cause of the listed runs; `marker-invalid`, check who wrote or edited the named comment, then delete it or take the issue out of the factory; when neither the user nor the Lair wrote or edited it, a session running as the user did, so end that session, and reset the key if it could read `control/`; `marker-missing`, remove `lair:claimed` from the named issue or take it out of the factory; `scanner-error`, start `claude` by hand in `scan/cwd/` to see why the scanner cannot start; `too-large`, handle the named issue by hand and take it out of the factory; `user`, the user's own. To take an issue out of the factory, the user removes its `lair:*`, `readiness:ready` and `readiness:implementation` labels.
  - `state-root` is a report-only cause code: the queue report gives it, and the Lair never writes it to the file.
- **Queue report.** Lines under invariant Lair-written text: `lair-queue v1 session=<hex> at=<UTC time>`; `halted: <cause code>` or `halted: no`; one `held: <cause code>` line per halt held in memory; `claims: ok` only when tick step 4 ran its claim step, else one `claims: blocked <code>` line per reason that skipped it: `halted` when the tick has a halt-file entry, a halt held in memory or an unavailable halt read, `sweep-pending` while the start-up sweep has not ended, `ready-too-large` when the Lair issue list is `too-large`, `lane-busy` when the lane read finds an open non-draft Lair pull request, `breaker-undecided` when a breaker read was unavailable or `too-large`, and `read-unavailable` when a read of another guard of tick step 4 was unavailable, the lane read or a reconcile-set read the start-up sweep waits on; `ready: <count>`, or `ready: too-large` when the Lair issue list is `too-large`; one `issue <number>: <stage> <code>[,<code>...]` line per ready-labeled issue that failed; and, when `ready` is 0, `hint: run hivemind:triage-backlog`. `<stage>` is `admission`, `snapshot-error`, `readiness`, `check-error`, `scan`, `retake` or `marker`. A reason code that does not match `^[a-z0-9][a-z0-9-]{0,63}$` prints as `unknown-reason`. `halted:` gives the cause of the halt file, or, with no file, of the oldest halt held in memory. A halt is held only while its write fails (Halt file). A halt's cause is given by the `halted:` and `held:` lines; `claims:` gives only the code `halted`. When the halt read is unavailable, the report prints `halted: state-root` and no issue lines. The Lair prints it to its tmux window on start, on each tick that finds nothing to claim, on each tick whose claim step a `claims: blocked` reason skipped, and on each tick where a ready-labeled issue fails, and at those times writes it to `control/cache/queue-report.txt` under invariant Unavailable reads.

### Assumptions about #630

- **Governance edits for unattended runs.** #630's governance edits also cover the scanner session as a caller of `hivemind:injection-scan` whose suspect handling is the verdict token, not the escalation in When Classified as injection-suspect, and add it, with the Scanner prompt's table, to the skill's Caller Mapping.
- **Containment of the key and the halt file.** No session the Lair starts, strains and remediation strains included, can read, write or delete anything under the state root's `control/` directory, by any tool, Bash included. The scanner session reaches only its own scan files and the plugin folder, under its own settings, and so no `/proc` entry.
- **Process reach.** No strain or remediation strain the Lair starts can see or open the Lair's processes or their `/proc` entries: the controller, and every child it runs, such as the SHA-256 tool that reads the padded key on its standard input. On Linux each strain and remediation strain runs in a sandbox with its own PID namespace, such as `bubblewrap --unshare-pid`, and #630's launch starts none without it (the user's answer of 2026-11-22). Where the platform offers no such sandbox, macOS among them, the proposed process-reach residual under Changes to shared documents applies. The scanner session is not #630's: its own settings keep it to its own scan files (Containment of the key and the halt file).

ADR-0045 decision 4's `Stop` hook is its source. When the hook does not fire, no idle signal comes, and the budget check ends the run `timed-out`; this replaces the solution design's stall fallback.
- **Tmux reach.** No session the Lair starts can reach the tmux server that holds the Lair's own window or the scanner's server on `control/scan.sock`, so none can send keys to either.
- **Orphaned strain sessions and worktrees.** The start-up sweep of ADR-0045 decision 17 also removes orphaned sessions and worktrees. #630 owns that removal for strain sessions and worktrees, and the strain-session lookup the crash and orphan rules read. This design owns the sweep of claims, and Start removes the scanner's leftovers.
- **Result file per strain.** A strain can write only its own result file, named for its run id, and no other strain's.

## Trust boundaries

- **Markers.** A marker counts only when the Lair's login wrote it, it is unedited, it carries the claim nonce and its signature verifies under the Lair's current key. The login check alone cannot tell the Lair from a strain, since both act as the user ([ADR-0045 residuals](../../adr/0045-lair-software-factory.md#residuals)); the signature can. An outsider's comment is never a candidate, so outsiders cannot forge a marker or trip the halt. A candidate under another key is foreign and halts nothing. The signature covers the payload, not the readable text, which invariant Lair-written text governs.
- **The key.** It is a file only the user's account can read, mode 0600 under `control/`. The sessions the Lair starts, strains, remediation strains and the scanner, cannot reach it, by #630's containment and the scanner's own settings, nor reach the key bytes in the Lair's processes, by #630's PID-isolating sandbox for strains on Linux (the user's answer of 2026-11-22) and the scanner's own settings. Any session that runs as the same operating-system user and is not started by the Lair, a brood strain or an interactive session, can read it and sign markers that count, and so can a Lair-started session that escapes its containment. The user declined a separate operating-system account for the key on 2026-11-21. On a platform with no such sandbox, macOS among them, a Lair-started strain can read the key out of the Lair's processes and fake a marker, such as a "run succeeded" outcome. Both are proposed as dated ADR-0045 amendments under Changes to shared documents.
- **The scanner session.** It receives the captured text as data, through a file, with no tool that can act outside its verdict line: no command, write, fetch, delegation, MCP server or hook. The verdict is a filter, not a boundary: an injected scanner can write the clean token, and the strain that then runs stays inside #630's containment. A scanner can never write a clean token for another scan, because the token names its scan id.
- **The strain result.** A signed outcome marker records what the Lair accepted from a result file. A strain writes only its own result file (#630), and #631's checks decide what is accepted; the signature adds no trust to the strain's own claims.
- **The halt file.** Only the user removes it. Sessions the Lair starts cannot reach it (#630), so a Lair strain cannot re-arm the Lair. A same-user session outside the Lair can, under the same proposed residual as the key.
- **The queue report and marker text.** Under invariant Lair-written text, no Lair-written string is an injection path into the user's terminal, a tmux pane, a scanner prompt or a later Lair reader.
- **Admission.** ADR-0045 decision 10 and its amendment stand. A ready label applied by hand on a parked issue, by a user with write permission, is the user's re-admission (ADR-0045 decision 11), which invariant Markers and labels respects; the same label from an actor without write permission neither admits the issue nor stops the reconciler's repair.

## Lifecycle

Start runs once, in this order. Each step that fails refuses start: the Lair prints the step's failure code, under invariant Lair-written text, and exits non-zero.

1. Check that the platform is Linux or macOS; that `flock`, `tmux`, `jq`, `gh`, `git`, `od`, `base64`, `perl`, `claude`, a SHA-256 tool (`sha256sum`, else `shasum -a 256`) and a timeout tool (`timeout`, else `gtimeout`) are on `PATH`; that `base64` decodes a fixed test string with `-d`, else with `-D`, the flag the Lair then uses; and that `/dev/urandom` reads. No write comes before this check. Failure: `tool-missing`.
2. Read the repository's GraphQL node id and the viewer login, the Lair's login of the counting rule. Failure: `github-unavailable`.
3. Resolve the state root from the password-database home and the node id, under Lair state root, and check that the path matches the state-root pattern of invariant Lair-written text and that the path of `control/scan.sock` is at most 103 bytes, the shorter socket-path limit of the two platforms. Failure: `state-root-unsafe`.
4. Create the state root, `control/` and `control/lock` when absent, both directories with mode 0700, then run the `lstat` checks of Lair state root. These are the only writes before the lock is held (invariant Lock scope). Failure: `state-root-unsafe`.
5. Take the lock. Failure: `lock held`.
6. Generate the session id. Failure: `random-unavailable`.
7. Remove the scanner's leftovers: kill the tmux server on `control/scan.sock` when one answers, remove the socket and every `scan/<scan-id>/`, then create `scan/`, an empty `scan/cwd/` and `control/cache/` when absent. Failure: `scan-cleanup-failed`.
8. Load the key. First remove a leftover `control/marker.key.new` under Marker signer and verifier. When `control/marker.key` has an entry, read it under the key file checks. When it has none, read the Lair issue list and the comments of each issue on it, and sort each Lair-login marker candidate:
   - a candidate whose first line matches the marker form and whose payload decodes with `v` 1 and a `kid` matching its pattern is named by that `kid`, and is retired when this start's `--retire-kid` names it;
   - any other candidate is malformed and has no `kid` to retire, so the refusal names its issue with `kid` `malformed`; the user deletes the comment or takes the issue out of the factory.

   When a candidate is not retired, refuse with `key-missing`, naming each such issue and `kid`. When the Lair issue list, or an issue's comments, are longer than 10 pages of 100, refuse with `too-large`, naming the issue, or `list` for the Lair issue list; the user handles that issue by hand and takes it out of the factory. Otherwise create the key under Marker signer and verifier, then read it. Failures: `key-invalid`, `key-missing`, `too-large`, `key-create-failed`, `github-unavailable`.
9. Check the signer against the RFC 4231 test vector. Failure: `signer-check-failed`.
10. Check that `control/` can be written: remove a leftover `control/write-check`, create it by exclusive create, write one byte to it, flush it to disk, and remove it. So Start refuses while a halt write would fail for `control/` itself. Failure: `state-root-unsafe`.

The user's key reset: delete `control/marker.key`, then start with `--retire-kid <kid>`, once for each `kid` the `key-missing` refusal named. Before it, the user ends every strain the old key's Lair started and takes each named issue out of the factory, or leaves it for re-admission. A retired `kid` is not stored: it only lets this start create the new key. After that, every marker under the old `kid` is foreign under the counting rule: it never counts and never halts. An issue that still carries `lair:claimed` halts the Lair with `marker-missing` until the user handles it. The `key-missing` check reads only the Lair issue list, which holds open issues only, so a closed issue's markers never block a new key.

Ticks run one after another, each starting 60 seconds after the last one ended, by a relative sleep. Each tick reads what its steps need, under invariant Unavailable reads:

- The reconcile set is the Lair issue list of invariant Claim state, issues whose only label from that list is `readiness:ready` included, so the start-up sweep reaches a claim that stopped before its first label write. Each tick reads each issue on it once for steps 1 to 3, and the reconciler, run end and the run checks compute from that read. Before each GitHub write they make, they re-read that write's guards under invariant Write guards.
- The breaker's reads are the issues of the window's runs it reads newest first and of the runs whose end time it does not hold, under the halt and the breaker below. An issue that is both a breaker read and in the reconcile set is read once for steps 1 to 3 of the tick, and both use that read.
- A candidate's snapshot, and the re-take of the one claim attempt a tick makes, are reads of their own. The re-take reads the breaker's issues again, newest first under the same stop rule, so it sees every outcome marker written after step 1.
- A read the Lair cannot complete, a GitHub error, a rate limit, a secondary rate limit or a timeout among them, is unavailable, so an unavailable read of any claim guard blocks the claim; an unavailable lane read, or a reconcile-set read the start-up sweep waits on, gives the queue report `claims: blocked read-unavailable`, and an undecided breaker gives `claims: blocked breaker-undecided`. A snapshot that cannot be read whole in the tick is not claimed this tick; one longer than 10 pages of 100 is `too-large`.
- A Lair issue list that is `too-large` gives no reconcile pass that tick: the tick reconciles no issue, claims nothing, and the queue report prints `ready: too-large` and `claims: blocked ready-too-large`. Run end and the run checks still read the issues of the runs this session launched.
- The exact read and rate limits, the pages a tick reads and the back-off after a rate limit, a wait longer than 60 seconds before the next tick included, are #608's, with a test that a rate-limited tick claims nothing and the next tick resumes.

Each tick runs in this order, every guard under invariant Unavailable reads:

1. Check the lock path, read the halt file, write each halt held in memory, and evaluate the breaker.
2. Reconcile the reconcile set under invariants Claim state and Markers and labels, halted or not. This is ADR-0045 decision 2's per-tick reconcile. The session's first pass that reads every issue of the reconcile set with a value is also the start-up sweep of ADR-0045 decision 17 for claims, and no claim is made before it ends.
3. Run end, then the budget check and the stall check, then the stages other slices own: the merge lane and park answers. Run end comes first, so a run whose result file exists is recorded with its own outcome and is never ended `timed-out` or `stalled`.
4. Evaluate candidates and claim at most one, only when the start-up sweep has ended, the halt read is clear, no halt is held in memory, the breaker is decided and has not tripped, and the lane read finds no open non-draft Lair pull request. A claim step skipped for any of these reasons gives the queue report its `claims: blocked` line per reason, and only a tick that ran its claim step prints `claims: ok` (Queue report).

The claim sequence, for one candidate:

1. Take the snapshot. Check admission (ADR-0045 decision 10 and its amendment; the PRD Admission criterion), including the edit rule under Contracts and seams; that the admitting `readiness:ready` labeled event is newer than the issue's latest counting outcome marker, and that the issue holds no counting handoff marker (invariant Markers and labels); that the issue holds no open claim (invariant Claim state); and that no live strain runs for it. A `too-large` snapshot is reported with stage `snapshot-error` and code `too-large`, and the issue is not claimed.
2. Run the readiness check on the snapshot. Only a pass goes on.
3. Generate the claim nonce and scan id, capture the text, and compute `body_sha256`.
4. Run the scanner session. Launching it is an action, not a read: a scan directory that cannot be created or a scanner session that cannot start is a scan error. A clean token goes on. A suspect or malformed verdict hands the issue off: a handoff marker, then the `lair:handoff` label, with no other label changed. Before the handoff marker, the Lair takes every claim-relevant field again, the handoff's re-read under invariant Write guards, since a scan can take 300 seconds; when any differs from the first take, the attempt ends with no write, counted as a step 5 end. The Lair never runs a handed-off issue (ADR-0045 decision 10; invariant Markers and labels). A scan error leaves the issue unclaimed, with no new label and stage `scan` in the queue report.
5. Take every claim input and every tick guard again, as Snapshot under Contracts and seams defines them. When any of them differs from the first take, the attempt ends with no write, and the next tick evaluates the issue again. After 3 such ends for one issue in a session, the Lair stops evaluating it for the rest of the session and reports it with stage `retake` and code `inputs-changing`, so a changing issue costs at most 3 scans per session.
6. Write the claim marker, and hold its nonce, issue, claim time and the tick count in memory as a run this session launched.
7. Add `lair:claimed`, then add `readiness:implementation`, then remove `readiness:ready`, then remove `readiness:needs-decision` when the issue carries it, as on a re-claim after a park.
8. Spawn the strain at the claim marker's `trunk` commit, and hold the spawn in memory by run id.

At run end the Lair writes the outcome marker first, carrying the run's id, holds the run's end time in memory, then writes the labels of #631's mapping, each write under invariant Write guards. Run end writes no outcome marker for a run whose claim marker does not count (Reader failure direction). On an answerable park, a `decision` or `fact` park that is not the issue's third, the issue moves to `readiness:needs-decision` and keeps `lair:claimed`, so triage still skips it (ADR-0045 decision 16). This answers A3-17. The user re-admits it by applying `readiness:ready` by hand, under invariant Markers and labels. An `approval` park or a third park takes the labels of #631's mapping, `lair:handoff` among them (ADR-0045 decision 7; invariant Markers and labels).

The reconciler applies invariants Claim state and Markers and labels, with these rules of its own:

- A crashed claim is ended whatever the issue's pull requests: an open claim whose strain session is gone with no result file is a crash with a draft or open pull request too, a re-claim's draft pull request included.
- The `crashed` outcome marker of a crashed claim carries `stage` `claim-labels` when the claim's label writes were incomplete, `spawn` when the claim marker's `session` is the current session and this session holds no spawn of its run id in memory, and `run` otherwise. This covers a write that failed, a write whose response was lost, and a claim left by an earlier Lair session alike.
- Under invariant Claim state a finished run whose result file is unconsumed still has a live strain, so step 2 never ends it `crashed`; run end records it in step 3 of the same tick. When that outcome marker's response is lost, the marker still counts, so the next tick repairs its labels and run end writes no second marker.
- A counting outcome marker whose labels do not match #631's mapping gets the mapping's labels again, except on an issue the user re-admitted, which invariant Markers and labels skips. A counting handoff marker without `lair:handoff` always gets the label again.
- A Lair issue whose snapshot is `too-large` halts the Lair with cause `too-large`.
- Every label write is idempotent.
- The reconciler computes each issue's verdict from the tick's shared read, and makes each outcome marker and label write under invariant Write guards: a `readiness:ready` labeled event by an actor with write permission that appears after the shared read is seen by the re-read, so no mapping write removes the user's re-admission; a strain session or result file that appears after the shared read is seen by the re-read too, so no `crashed` outcome marker or orphan label is written for a live strain.

The run checks end a run that has a strain session the Lair launched, under Reader failure direction, no result file and no counting outcome marker of its run id. Each writes the outcome marker, then the labels, each under invariant Write guards, whose re-read takes the strain session, the result file and, for the stall check, the idle signal again, then ends the session, so a lost session end leaves no open claim. A result file that appears before the write skips it, and run end records the result on the next tick. When the issue's read, or the re-read before the outcome marker, is `too-large`, the run gets no outcome marker: a session this Lair session launched for it is ended at its budget or on its idle signal with no marker, as for a run whose claim marker does not count, and the Lair holds the time it ended that session as the run's end time in the session records; no other session is ended, and the issue's `too-large` halt stands. A session the Lair launched whose run has ended, by a counting outcome marker of its run id or, for a run whose claim marker does not count or whose issue is `too-large`, by the Lair ending it with no marker, is ended again on each later tick while it runs, with no new marker:

- The stall check ends the run `stalled` on #630's idle signal (Assumptions about #630).
- The budget check ends the run `timed-out` when its elapsed time since its start exceeds the budget. A run starts at its claim, or, for a remediation run, at its launch (Assumptions about #631). Elapsed time is the larger of two values, so neither a clock set back nor a slow clock lengthens a run:
  - the wall-clock time since the start: since the claim or launch time held in memory for a run this session launched; for a claim an earlier session made, since the counting claim marker's `at` once a read has given it, unless that `at` is more than 300 seconds ahead of the Lair's clock, when it is not used; for a remediation run an earlier session launched, none, so the floor alone times it;
  - a floor that only grows: 60 seconds for each tick started since the run's start, or, for a run an earlier session launched, since this session's first tick. Each tick follows a relative sleep, which setting the wall clock neither shortens nor lengthens (POSIX `clock_settime`).

  An unavailable read never pauses the clock. A malformed `at` makes its marker invalid under the counting rule.

The halt and the breaker:

- With a halt, a halt-file entry or a halt held in memory, the tick evaluates no candidate; reconcile, run end, the run checks, the stages of step 3 under their owners' rules, and the queue report still run. A halt that appears after the claim marker is written takes effect from the next tick, and that claim completes.
- The breaker counts the runs this session launched and ended, by run id. Each tick it is recomputed from GitHub, never held from an earlier tick (ADR-0045 decision 17). It reads, through the verifier, the outcome markers of the window's runs newest first, by the end time the session records hold, and stops once it has read 3 counted runs, each a `complete` or a failure; a `parked` or `blocked` run is skipped and the read goes on, and no run older than the third counted run is read. Runs of equal held end time are read together. It also reads each run this session launched in the current window whose end time it does not hold, such as one whose outcome marker's response was lost; a run with no held end time is in the current window when its claim or launch time is no earlier than the window's opening time, and is not read once a later window opens. A counting outcome marker read for such a run gives its `ended_at`, which the Lair then holds, and the window rule then places the run by it. It decides on the most recent counted runs it read, the last 3 in ended order. Ended order is the outcome marker's `ended_at`, then its comment's `createdAt`, or, for a run whose outcome marker does not count, the end time held in memory. A run is in the window when it ended no earlier than the window's opening time. In the window, three consecutive failures trip it: a `failed`, `crashed`, `timed-out` or `stalled` outcome, or an outcome marker that does not count. A `parked` or `blocked` outcome is skipped: it neither counts nor ends a streak. A `complete` outcome ends a streak. Each tick sorts the outcome markers it read afresh, so a run that ends out of order takes its place by `ended_at`, and no streak is missed. A claim an earlier session made, ended `crashed` by this session's reconciler, is not a run this session launched and is not counted. The window opens at the session's first tick, and again at each tick that finds the halt file gone after it was present while no halt is held in memory. A breaker read that is unavailable or `too-large` leaves the breaker undecided under invariant Unavailable reads, so the tick claims nothing and the queue report prints `claims: blocked breaker-undecided`. A run with a held end time older than the third counted run is never read, so its read never leaves the breaker undecided; a run with no held end time is read only in the window it was claimed or launched in, so its read stops leaving the breaker undecided once a new window opens. A run this session launched that is still running on a `too-large` issue gets a held end time when the run checks end its session with no marker. An outcome marker written after step 1, a `crashed` marker of the reconcile pass included, is seen by the breaker's re-take before any claim marker and by every later tick.
- A breaker trip and each tripwire (`marker-invalid`, `marker-missing`, `scanner-error` after three consecutive scan errors in a session, and `too-large`) write their own cause to the halt file at once, under Halt file in Contracts and seams: by exclusive create when the halt read finds no entry, else by appending a record to the entry, the user's own or an earlier cause's. No trip waits on the user deleting another entry.
- A halt whose write is not made, because the halt read is unavailable or the create or append fails, is held in memory, one per cause, and the queue report gives it. A held halt stops claims for the session like any halt. Each tick writes every held halt again, oldest first, by create or append, and a held halt ends only when its own record is written. Deleting the file never reopens the breaker's window while a halt is held.
- No restart claims past a held halt. When the write failed on an entry the Lair cannot append to, such as a directory, a symlink or a file the Lair cannot write, that entry halts every later start too, until the user deletes it. When it failed because `control/` cannot be read or written, Start refuses while that lasts (Start steps 4 and 10). A held halt is lost only when the controller ends while its write fails and `control/` becomes writable before the next start; no file could hold it then, and the queue report on the Lair's terminal is its only record.

| Issue changed during evaluation | Any claim input or tick guard differs on the re-take before the claim marker (claim sequence under Lifecycle). | No write; the issue is evaluated again next tick, up to 3 ends per session, then reported with stage `retake`. |
| Stale design, or an epic | The readiness check fails, or the issue carries `type:epic`. | Not claimed and given no new label. Reported with its stage and reason codes. |
| Readiness check error | A non-zero exit, a malformed result, or no result within 60 seconds. | Not claimed, no new label, reported with stage `check-error`. The next tick starts its checks after this issue. |

| Second Lair on another machine or account | Its markers carry another `kid`, or another login. It runs in another lock scope (invariant Lock scope). | Its markers are foreign or not candidates. | Halt not written | The halt read is unavailable, or the exclusive create or the append fails: `control/` cannot be written, or the entry is not a regular file the Lair can write. | The halt is held in memory, one per cause, stops claims for the session, and the queue report gives it. Start refuses while `control/` cannot be written, and an entry the Lair cannot append to halts every later start until the user deletes it. |

| Breaker undecided | A breaker read is unavailable or `too-large`. | No claim that tick, and the queue report prints `claims: blocked breaker-undecided`. The next tick reads again. When a read stays `too-large`, as for a closed issue with too many comments, the user opens a new window by creating the halt file and deleting it after the next tick, once the run has ended; a run that ended before the new window opened is out of it (Lifecycle). |
| Circuit breaker trip | Three consecutive counted outcomes in the current window. | A halt record with cause `breaker` and the runs, in a halt file created for it or appended to an existing one; only the user deleting the file re-arms the Lair. |

## Verification strategy

The tests are the PRD's [Testing Decisions](../../prds/autonomous-ready-issue-loop.md#testing-decisions); this section adds the claim-integrity cases and where they live. All run on recorded GitHub states, with no live GitHub, and fixtures live under `tests/lair/`. Each suite lands with the slice named in its heading; a case that tests another slice's part lands with that slice, as marked. The races between a guard's re-read and its write are proven by #608's generated write-guard test, and a further timing detail it finds is fixed in that build slice under this design's invariants.

- **`tools/test_lair_markers.sh`, #605.**
  - Sign then verify, and the RFC 4231 HMAC-SHA256 test vectors.
