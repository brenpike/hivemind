# Settled approval and opt-in auto-merge in the post-PR watch

**Status:** accepted, 2026-11-20. Amends ADR-0026 (the consequence "the merge action always stays with the human"). Extends ADR-0043 decision 5.

## Context

The post-PR watch (`hivemind:github-review-loop`) ends clean on a Reviewer Approval (ADR-0043 decision 5). An in-scope Automated Reviewer's latest review is `APPROVED`, or is `COMMENTED` with no inline comments, or the bot left a 👍 on the PR. That covers a Copilot review with no inline comments, whatever its text says.

One case is not covered. A bot leaves inline threads. HIVEMIND fixes and resolves them. The bot never reviews again. No approval ever fires, so the watch idles until `watch-window-elapsed`. The user then has to see that the PR is done and merge it by hand.

The user asked for two things: an approval that fires in this case, and an opt-in merge at the end of a clean watch. The decisions below come from a plan-interrogation session with the user on 2026-11-20.

## Decision

### The user's decisions

1. **Settled approval.** The change-detect poll gets a clock-based marker, `REVIEWER_SETTLED`. It fires when all of these hold:
   - No marker has printed for a fixed settle period, `SETTLE_SECONDS` (600, about 10 minutes), since the arm or the last `CHANGED` or `CI_FAILED`.
   - An in-scope Automated Reviewer has reviewed or 👍'd the PR, and no latest review of any author is a standing request for changes (decision 14).
   - Every review thread is resolved or ends in HIVEMIND's own reply, and the thread read is complete.

   It reads no review text. The skill handles `REVIEWER_SETTLED` exactly like `REVIEWER_APPROVED`: a confirmation pass, the QUIET-EXIT CHECK, then `approval-clean`. The seed shape and the clock reads are unchanged.
2. **A fixed script merges, with no AI judgment.** The script is `merge-approved.sh`, inside the watch. The skill runs it once after an `approval-clean` end. The overlord makes no merge decision; the script's checks are the whole rule.
3. **`--admin` sits behind a second setting.** `HIVEMIND_AUTO_MERGE_ADMIN` allows it. The script uses `--admin` only when the plain merge is refused, the setting is set, and its own check saw every check pass.
4. **Merge only after approval with every check green.** The PR must be approved and the head commit's check rollup must be `SUCCESS`, CI included. The merge call uses `--match-head-commit`, so a push after the check cannot be merged unchecked.

### The run's own calls

5. **Pending CI keeps the watch running.** Pending or failed checks never merge and never end the watch. A CI failure still gets fixed, and the merge is tried again at the next settled approval.
6. **No checks means no merge.** A head commit with no check rollup is not green.
7. **Any open thread blocks the merge.** A thread that is not resolved and does not end in HIVEMIND's reply stops the script.
8. **The setting value names the method.** `HIVEMIND_AUTO_MERGE` is `merge`, `squash` or `rebase`. Unset or empty means off. Any other value is refused, and nothing merges.
9. **The script rechecks approval itself.** It does not trust the skill's end reason. It checks again that the PR is open and not a draft, that an in-scope bot reviewed or 👍'd and no latest review of any author is a standing request for changes (decision 14), that every thread is settled, and that the rollup is `SUCCESS`.
10. **The skill routes the script's one line.** The skill runs the script only after an approval return whose QUIET-EXIT CHECK reports `UNCHANGED`. No other end runs it, `merge-advised` included. `MERGE=off` ends `clean`, as before. `MERGE=merged` or `MERGE=merged-admin` ends `pr-merged`, through `loop-state.sh token-map STATE=MERGED`, with the line under `Issues` (decision 16 says when the script prints them). `MERGE=skipped:*`, `MERGE_ERROR=`, a non-zero exit or a refused call ends `clean`, with the line under `Issues` and a `Next action` that tells the human to merge.
11. **A wait keeps watching in the current window.** `MERGE=wait:*` ends nothing. The skill arms the poll again with the pending seed for the time left in the current idle window. That arm opens no new window and captures no seed, so a PR whose CI never turns green ends at `watch-window-elapsed`.
12. **An empty `HIVEMIND_AUTO_MERGE_ADMIN` is off.** The setting is checked by presence, like the other `HIVEMIND_*` presence settings, and an empty value counts as unset. Only a non-empty value allows `--admin`.

### Recorded review decisions

13. **A fresh blocked or behind read is the refusal signal for `--admin`.** Decided by the run under `plugin/governance/decision-autonomy.md` (Review Calls), on a local-review finding, 2026-11-20. After a failed plain merge the script does not read the error output and does not prove why the merge failed: a network, login or CLI error counts the same as a branch-protection refusal. The `--admin` retry runs only when a fresh read shows the same head, GitHub's merge state `BLOCKED` or `BEHIND`, and every gate passing again. GitHub then reports that a plain merge would be refused anyway, so the admin merge happens under the conditions decision 3 allows. Parsing the tool's error text was rejected as fragile text matching. A finding that only says the first failure may not have been a branch-protection refusal contests this decision and is a repeat.
14. **Approval is the review state, not author presence.** Decided by the run under `plugin/governance/decision-autonomy.md` (Review Calls), on a local-review finding, 2026-11-20. The finding: the merge gate and the poll's settle evidence counted a bot's presence among the latest reviews as approval, so a bot review that requests changes, or a human or null-author one, could merge. One shared module def, `has_settled_evidence` in `reviewer-identity.jq`, is now the only settled-evidence verdict, and the settle check and the merge script's approval gate both call it. Every latest review of any author, null-author rows included, must be in the allowlist `APPROVED`, `COMMENTED` or `DISMISSED`; `CHANGES_REQUESTED`, `PENDING`, a missing state or an unknown state blocks. Approval then needs an in-scope bot whose latest review is `APPROVED` or `COMMENTED`, or an in-scope bot's 👍. A human's `CHANGES_REQUESTED` therefore also blocks the merge, failing closed. A blocked merge prints `MERGE=skipped:no-approval`, as before; no setting, output line or marker is added. `REVIEWER_APPROVED` is unchanged (ADR-0043 decision 5): it can still fire on one bot's approval while another author's latest review requests changes, but that only ends the watch, and the merge script now refuses the merge.
15. **A review state change in the seconds before the merge call is a known limit.** Decided by the run under `plugin/governance/decision-autonomy.md` (Review Calls), on a local-review finding, 2026-11-20. The merge script reads reviews, threads, draft state and checks, then calls `gh pr merge`. A review that requests changes, or a reopened thread, landing between that last read and the merge call, plain or `--admin`, is not seen. `--match-head-commit` pins only the head commit; GitHub offers no merge call that also pins review or thread state, so no client-side check can close the gap, and the window is a few seconds. The code is kept as it is. Requiring GitHub's branch protection for the plain merge was rejected: it adds a protection read, does not cover the `--admin` retry decision 3 allows, and only narrows the plain path. A finding that only says review or thread state can change between the script's last read and its merge call contests this decision and is a repeat.
16. **A merge is what GitHub shows, not the merge call's exit status.** Decided by the user on a GitHub review finding (https://github.com/brenpike/hivemind/pull/602#discussion_r4650841549), 2026-11-21. In a merge-queue repo `gh pr merge` exiting 0 only queues the PR; it is not merged yet. After every merge call that exits 0, plain or `--admin`, the script re-reads the PR. It prints `MERGE=merged` or `MERGE=merged-admin` only when the state is `MERGED`, and `MERGE=wait:merge-pending` otherwise. Decision 11 routes that line, so the watch keeps running and the poll's `STATE=MERGED` ends it at `pr-merged`. A failed confirm read prints `MERGE_ERROR=`. A finding that asks to end the watch on the merge call's exit status contests this decision and is a repeat.

## Considered options

- **Read review text for a settled verdict**, such as Copilot's "Approval Recommended". Rejected: product wording in code and text matching on external content, as ADR-0043 rejected.
- **Ask the reviewer for a new review after the fixes.** Rejected: ADR-0043 decision 7, the loop never requests a review.
- **A long settle period, or one set per repo.** Rejected: the user chose a short fixed period. A setting adds surface for a value nobody has asked to tune.
- **The overlord judges whether to merge.** Rejected: the user chose no AI judgment. A fixed script is the same every run and can be tested.
- **`--admin` under the same setting as the merge.** Rejected: bypassing branch protection is a bigger grant than merging, so the user put it behind its own setting.
- **Merge while CI is pending, or with GitHub's own auto-merge.** Rejected: the user chose to merge only when every check is green, and the watch must stay up to fix a CI failure.
- **One on/off setting plus a separate method setting.** Rejected: one value that names the method is enough.
- **Read every latest review as approval evidence, whatever its state.** Rejected: a review that requests changes, or a human or null-author review, would count as approval and could merge. Decision 14 keys approval on the review state instead.
- **Drop the script's merged result and let the poll end every merge.** Rejected: the poll checks its deadline before it reads the PR, so a merge that lands late would end at `watch-window-elapsed`, and the `--admin` note would be lost.
- **Record that auto-merge does not support merge queues.** Rejected: queue repos would keep the false `pr-merged` end, and decision 16 handles them.

## Consequences

- With `HIVEMIND_AUTO_MERGE` unset, nothing merges. The merge stays with the human, as before.
- With it set, ADR-0026's consequence "the merge action always stays with the human" no longer holds for that repo. The overlord still never decides a merge, and a merge recommendation outside the watch stays Tier-A. Only the fixed script merges, and only after a clean watch.
- With `HIVEMIND_SKIP_PR_WATCH` set (ADR-0029), no watch runs, so nothing merges.
- A watch that ends any way other than `approval-clean` merges nothing.

### Residuals

- **A slow bot re-review can be cut off.** A bot that starts a new review more than 10 minutes after the last fix can find the PR already merged. Its findings then need a new PR.
- **An unreviewed push by another account can merge.** If another account pushes to the branch, the push can merge once its checks are green and approval fires again. No bot needs to have reviewed that push.
- **A stray bot 👍 can now lead to a merge.** Under ADR-0043 a bot's 👍 makes it an Automated Reviewer. With the setting on, that 👍 can lead to a merge when no thread is open and every check is green. Before this ADR it could only end the watch.
- **Auto mode can refuse the merge call.** The permission system may refuse the `merge-approved.sh` call in auto mode. The script's own `gh pr merge` is not judged on its own. A refused call never runs the script, so the skill reports the refusal and the PR stays open for the human. *(2026-11-25: corrected, see Amendment 2026-11-25.)*
- **Committed settings turn auto-merge on in brood worktrees.** `HIVEMIND_AUTO_MERGE` set in the committed `.claude/settings.json` is inherited by every brood worktree, so every strain's PR can merge. `spawn-brood` also copies the coordinator's `.claude/settings.local.json` into each strain worktree at spawn, so a key set there reaches every strain too, as it was at spawn. Neither file keeps the setting to one checkout. *(2026-11-25: corrected, see Amendment 2026-11-25.)*
- **A merge queue can outlast the idle window.** A queue slower than the time left in the idle window ends the watch at `watch-window-elapsed` while the PR is still queued. A queue that drops the PR leaves it open for the human.

## Amendment 2026-11-21: the Lair controller runs the merge script (issue 631)

The user approved these changes on 2026-11-21 for the Lair's one merge lane ([ADR-0045](0045-lair-software-factory.md) decision 12). The full design is [merge-lane-design.md](../initiatives/autonomous-ready-issue-loop/merge-lane-design.md). Decisions 1 to 16 stand except where a decision below amends one.

17. **The Lair's tick may run the merge script.** Amends decision 2. Besides the watch, the Lair's tick (ADR-0045 decision 12) may run `merge-approved.sh`, but only for a Lair pull request and only after the tick's settle check (decision 18). The tick passes the merge settings it reads from the user's own settings files: `.claude/settings.local.json`, then `~/.claude/settings.json`, never the committed `.claude/settings.json`, as merge-lane-design.md defines.
18. **The tick's settle check equals decision 1.** Across ticks, the watch's change check against a cached snapshot must show no change for `SETTLE_SECONDS` (600). The script's own approval and thread gates (decisions 9 and 14) must then hold on its read. The tick never merges on a plain reviewer approval without that quiet period.
19. **An optional expected head.** Amends decisions 4 and 9. `merge-approved.sh` takes an optional sixth argument, the expected head. When the first read's head differs from it, the script prints `MERGE=wait:head-moved` and makes no merge call. Every merge call matches that head. The watch's five-argument call is unchanged.
20. **The tick routes its own result.** Amends decision 10. The skill's routing binds the watch only. The tick routes each `MERGE=` line by the table in merge-lane-design.md.

These stay unchanged: the gates, the `--admin` rule (decisions 3, 12 and 13), the one-line form of the output contract, and the watch's own call and routing. Decision 19 adds the error reason `MERGE_ERROR=bad-expected-head` to that contract, and gives `MERGE=wait:head-moved` a second meaning: the head check before gate 1.

The Consequences and Residuals read as follows for the tick:

- A Lair merge needs no watch. The consequences that tie a merge to a clean watch, and to `HIVEMIND_SKIP_PR_WATCH`, bind the watch only.
- The committed settings never reach the tick. The residual "Committed settings turn auto-merge on in brood worktrees" does not apply to a Lair merge.
- A head no Lair run recorded never merges a Lair pull request, as long as two assumptions of merge-lane-design.md hold: no other process can write a marker that passes the Lair's marker rule (Assumptions about #632), and every strain push is leased against the head the run expects, so no head built on another account's push is recorded (Assumptions about #630). Then the residual "An unreviewed push by another account can merge" does not apply to a Lair merge. Where either assumption does not hold, the residual applies, through a forged marker or through a fix-up run's recorded head.
- The tick makes no merge call in a repository whose trunk branch requires a merge queue; it sends such a pull request to batch review. It also makes none while a pull request is in the merge queue or has an auto-merge request. So the tick's own call queues a merge or arms an auto-merge request only when the trunk branch starts requiring a merge queue in the merge gap (merge-lane-design.md, Residual: a queued or armed merge), and the residual "A merge queue can outlast the idle window" binds the watch only. A queue entry or an auto-merge request that someone else made is outside the tick, like any merge another account makes.

## Amendment 2026-11-24: the review record gate (issue 619)

These changes give `merge-approved.sh` a review record gate, decided in the plan for issue 619 on 2026-11-24. Their input is [ADR-0046](0046-idea-to-ready-process.md) decision 7 and findings RR4-C1, RR4-1, RR4-2 and RR4-3 of the idea-to-ready [review record](../initiatives/idea-to-ready/review-record.md). Answer Q25 A moved merge-time enforcement on the plugin's merge paths out of the idea-to-ready design and into #619 ([solution design](../initiatives/idea-to-ready/solution-design.md), D28). That design and ADR-0046 are stamped by a passing record, and an edit would stale it, so they stay unedited and this amendment is where #619's merge-time enforcement is recorded. Decisions 1 to 20 stand except where a decision below amends one.

21. **The gate runs only on a docs pull request.** Amends decision 9. The script runs the record gate, step R, only when the pull request's file list touches `docs/prds/`, `docs/initiatives/` or `docs/adr/`, holds a renamed file, whose old path the read does not see, or overflows its first page of 100 files. Step R runs after gates 1 to 7 hold and before any merge call. Any other pull request is unchanged: no git call, no fresh read, and the same output as before.
22. **The fetch remote must name the repository it merges in.** Input: RR4-1. The script fetches from the first remote, in `git remote` order, whose name passes the identifier gate and whose fetch URL, read by `git remote get-url` with `insteadOf` applied, names `<OWNER>/<REPO>` on the gh host (`GH_HOST`, else `github.com`). With no such remote the script prints `MERGE=skipped:record-unread`, so a fork or a foreign base is never checked in place of the real one. The fetch takes the pull request head and the base branch with `--no-tags` and an empty `--refmap=`, so it writes no local branch and no remote-tracking ref.
23. **A fresh read before each merge call narrows the base race; the gap after it is a known limit.** Input: RR4-C1. `--match-head-commit` pins only the head, so GitHub can merge onto a base newer than the one verify checked. Merge mode checks against the base tip the first read saw, and fails a passing record whose stamped blob at that tip differs from its blob at the merge-base. When the gate holds, the script reads the pull request again before every merge call, plain or `--admin`. A new head prints `MERGE=wait:head-moved`, a new base `MERGE=wait:base-moved`, and a gate of 1 to 7 that now fails prints its own line. A base that moves between that read and the merge call, one gh call wide, is not seen. It is a known limit like decision 15: GitHub offers no merge call that also pins the base. It is bounded by the readiness check, which fails every slice of a stale record, so no slice of it is labeled ready or claimed. A finding that only says the base can move between the fresh read and the merge call contests this decision and is a repeat.
24. **The verify exit codes map to fixed lines.** Input: RR4-2. The script calls `hivemind_record_verify_merge <head> <merge-base> <base-tip>` from `record-verify.sh` and discards its output. Exit 0 continues to the fresh read. Exit 1 prints `MERGE=skipped:record-blocked`. Any other status prints `MERGE=skipped:record-unread`, as does a failure before verify: no tied remote, a bad base name, a failed fetch, a missing commit or no merge-base.
25. **Merge mode never skips a design the pull request changes.** Input: RR4-3. Each record the pull request adds or edits, and the record of every `docs/initiatives/<s>/` folder it changes, must meet the pass rule, delivered or not. A changed folder with no record fails. A close-out pull request, which marks a design delivered, edits a stamped document that no review re-stamps, so its record fails and the script prints `MERGE=skipped:record-blocked`. A close-out therefore merges by hand.

Decision 10 routes `MERGE=skipped:record-blocked` and `MERGE=skipped:record-unread`: the watch ends `clean` and tells the human to merge. Decision 11 routes `MERGE=wait:base-moved`. These are the three new output lines. `MERGE=wait:head-moved` gains a third meaning, a new head on the fresh read. The bootstrap error reasons gain `missing-readiness-check`, `unparseable-readiness-check`, `missing-record-verify` and `unparseable-record-verify`. The one-line form of the output contract, the gates 1 to 7 and the `--admin` rule (decisions 3, 12 and 13) are unchanged, except that on a docs pull request an `--admin` call also needs the re-read's base to equal the first read's.

The Consequences and Residuals read as follows for the gate:

- The Lair's tick inherits the gate through decision 17, since it runs the same script. The tick never auto-merges a pull request that touches docs paths, because #605's auto-tier floor sends it to batch review ([ADR-0045](0045-lair-software-factory.md) decision 12). For a Lair pull request the gate is a second guard behind that floor.
- The gate needs git and a checkout of the repository in the current directory. Without them the script prints `MERGE=skipped:record-unread`, and a docs pull request merges by hand.
- ADR-0046's residual "Human merge of a record that does not pass" stands. The gate binds `merge-approved.sh` only: a human with write permission can still mark a docs pull request ready and merge a record that does not pass. A push after ready that `merge-approved.sh` merges is now verified at merge time, up to the gap of decision 23.
- **The fetch overwrites `FETCH_HEAD`.** The gate's fetch writes `FETCH_HEAD` in the local repository and adds the fetched objects to it. `--no-write-fetch-head` would avoid that, but it needs git 2.29, and the script supports git 2.1 or later. No branch or remote-tracking ref changes.

## Amendment 2026-11-25: the merge grant and the refused-merge re-read (issue 674)

These changes fix two failures of the opt-in merge, decided in the plan for issue 674 on 2026-11-25. Decisions 1 to 25 stand except where a decision below amends one. The permission posture of decision 26 is recorded in [ADR-0010](0010-permission-allowlist-posture.md), Amendment 2026-11-25.

**The grant failure.** The watch skill's `allowed-tools` granted `merge-approved.sh`. A skill grant lasts only for the turn that invokes the skill: "The grant clears when you send your next message ... invoking the skill again re-applies it for that turn" (Claude Code skills docs; ADR-0010, Amendment 2026-11-14). The merge runs turns after the watch skill is invoked, so in auto mode the classifier judged the call and denied it (consumer PR #710).

**The PR #672 diagnosis.** On 2026-11-25 the watch on PR #672 printed `MERGE=skipped:refused`. GitHub showed the merge state `BLOCKED` with `REVIEW_REQUIRED`, Codex had 👍'd, CI was green, `HIVEMIND_AUTO_MERGE` was `squash` and `HIVEMIND_AUTO_MERGE_ADMIN` was `1`. The admin key was not missing: `spawn-brood` copies the coordinator's `.claude/settings.local.json` into each strain worktree at spawn, and a missing key prints `MERGE=skipped:blocked`. The maintainer merged with `--admin` by hand right after, and it succeeded, so GitHub accepts the bypass. So after the refused plain merge, the script's re-read saw a merge state other than `BLOCKED` or `BEHIND`, most likely `UNKNOWN` while GitHub recomputed it, and printed `MERGE=skipped:refused` without trying `--admin`.

26. **A per-turn grant from `hivemind:merge-write`.** Amends decision 2. A new model-only skill, `hivemind:merge-write`, runs no command. Its `allowed-tools` holds exactly `Bash(bash "${CLAUDE_PLUGIN_ROOT}/skills/github-review-loop/scripts/merge-approved.sh" *)`. The watch invokes it right before each merge call, so the grant holds in the turn that runs the script. The watch skill drops its own grant. A new skill, not `hivemind:review-writes`: that skill would hand merge reach to the reviewer subagent that invokes it, and it is pinned to exactly three grants. Invoking the watch skill again would reload its whole procedure.
27. **A refused call is `MERGE=skipped:permission-denied`.** Amends decision 10. When the permission system refuses the `merge-approved.sh` call, the script never runs, so it never prints this line. The skill writes it under `Issues`, and the watch ends `clean`. The `Next action` tells the human to merge by hand and names the rule `Bash(bash "<the script's full path>" *)` to add to `permissions.allow` in `.claude/settings.local.json`. This is the fallback when the grant does not reach the call (`docs/engineering-principles.md` P26).
28. **An unknown merge state is read again, and a refused `--admin` merge has its own line.** Amends decision 13. After a refused plain merge, a re-read whose merge state is `UNKNOWN` is read again, at most 2 more times, 5 seconds apart by default. A state that settles to `BLOCKED` or `BEHIND` takes the `--admin` path under decision 13's conditions. A state still `UNKNOWN` prints `MERGE=wait:merge-state-unknown`; decision 11 routes it, so the watch keeps running and the merge is tried again. A refused `--admin` retry prints `MERGE=skipped:admin-refused`, not `MERGE=skipped:refused`; decision 10 routes it, and the human checks that the account can bypass the branch rules and merges. Any other merge state still prints `MERGE=skipped:refused`. Chosen by the maintainer, option B.

The gates, the `--admin` conditions of decisions 3 and 12, and the one-line form of the output contract are unchanged.

The Lair's tick runs the same script (decision 17). Its routing table in [merge-lane-design.md](../initiatives/autonomous-ready-issue-loop/merge-lane-design.md) has no row for `MERGE=wait:merge-state-unknown` or `MERGE=skipped:admin-refused`, so until the tick design adopts them the tick takes its `MERGE_ERROR` route for either: no change, a retry next tick, bounded by the review wait. `MERGE=skipped:permission-denied` never reaches the tick, since the script never prints it. On a docs-touch PR whose `--admin` rerun follows two `UNKNOWN` re-reads, the script's reads and waits with the default delay take at most 280 seconds: 6 reads of 45 seconds and 2 waits of 5. That path also runs the record gate's fetch, bounded at 120 seconds, and record verify, so its whole worst case, about 400 seconds, can pass the design's 300-second child timeout. The path before this amendment, 4 reads and the fetch, already reached 300 seconds; the run decided on 2026-11-25 to keep the re-read bound at 2 and not to bound the whole run. A run the child timeout kills routes as `MERGE_ERROR` and is safe, because the next tick derives the merge state from GitHub (merge-lane-design.md, Decided for you, R32). The cost is a retried tick, and only when GitHub is slow enough that reads near their 45-second bound. A `HIVEMIND_AUTO_MERGE_REREAD_DELAY` above 5, set by the operator, lengthens the path the same way. Its read count now exceeds the design's "three reads", a figure the tick design adopts later, as for the other new lines. Decisions 26 and 27 bind the watch only. merge-lane-design.md is stamped by a passing record, and an edit would stale it, so it stays unedited, as in Amendment 2026-11-24. Its statements that the watch skill holds the grant and that the grant is unchanged describe the watch before this amendment.

Two residuals are corrected in place: auto mode refuses the `merge-approved.sh` call, not `gh pr merge`, and `.claude/settings.local.json` is copied into each brood strain at spawn, so a strain keeps the keys as they were at spawn and that file does not keep the setting to one checkout.
