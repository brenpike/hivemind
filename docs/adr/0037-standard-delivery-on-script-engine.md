# standard-delivery is the second workflow on the script engine

**Status:** accepted, 2026-10-20

## Context

ADR-0035 chose one Claude Workflow script per workflow. ADR-0036 put analysis-only on that engine as slice 1 and deferred the git questions to slice 2. Issue #409 tracks the work. Slice 2 moves the pre-PR part of standard-delivery onto the engine.

Three things in standard-delivery cost the user today. Every planner question ends the run as blocked. Every transition costs an overlord turn, and 52% of overlord tool calls are ledger bookkeeping. Git safety is written in prose. The slice must also avoid a new state machine in prose and side-effect agents that repeat their effects when a run is replayed (ADR-0035 decision 8, spike S5).

This ADR records the slice decisions, the user's three calls, the step invariants, and the results of spikes S11 and S12. It does not restate the rules. Each rule is stated once in its home file, named below as "Text:". Most homes do not exist yet; "Lands in:" names the PR in Landing PRs below that creates each one. This ADR also does not specify the fields, limits or step mechanics of code that does not exist yet. Where it names one, as in the hand-off table, that is an obligation for the landing PR, whose schemas and tests settle it. A review finding on such a detail is recorded as an obligation for that PR, in the hand-off table or under Deferred items, and is tracked under #409. It changes a decision or an invariant here only when it shows that the decision or invariant is wrong.

## Scope

This ADR governs:

- the new engine's standard-delivery workflow, from the request up to and including opening the PR;
- the committed git scripts behind the git skills, which both engines use;
- the interim start of brood children without the Workflow tool (decision 10);
- the removal of Bash from cerebrate (decision 1), which also changes the current engine.

The post-PR watch and pr-feedback-remediation stay on the current engine until slice 3. Every other ADR keeps the scope ADR-0035 gave it. New permission-engine facts are recorded in ADR-0010 under "## Amendment 2026-10-20: tool grants and prompts for workflow agents"; this ADR uses them and does not repeat them.

## Workflow outline

`hivemind:standard-delivery` runs these steps in code. The order and the routes between steps are code, the step invariants below hold at every step boundary, and each step's rules live in the homes the decisions name.

1. Facts: a runner runs the facts script, which reports the branch as it is so that the planner can plan what is left: branch state against a freshly fetched trunk, the branch's history against trunk, the branch's PR, and the text of any issue or PR the request names. Contract: `plugin/references/facts-schema.json` and the facts script's tests (PR2), which cover the "Facts to plan" row of the hand-off table below.
2. Plan: cerebrate returns a plan checked against a schema. Its questions and the plan acceptance go through `decide()` or the pause contract.
3. Branch: a runner creates or confirms the working branch.
4. Waves: code computes each ready wave and runs the workers in parallel.
5. Version bump: a runner runs the bump-type engine, and a drone makes the edit.
6. Validate: a drone runs the project's validation commands, with bounded fix rounds.
7. Local review: `hivemind:local-reviewer` runs, and a code table routes its exit reasons.
8. PR: a runner pushes through `push-branch.sh` and opens the PR or reuses an open one.
9. The overlord relays the message, applies the ADR-0029 watch rule, and hands the watch to pr-feedback-remediation on the current engine.

A workflow script cannot run a shell, so it sees only what agents report. The hard stops sit in the committed scripts, and the workflow reads their routing lines from a schema field and blocks when a line is missing or malformed.

## Step invariants

Five review findings on PR #419 had one root: a decision or step was written in prose without checking it against what its consumer requires, and each fix added one more field or action for the next review to probe (see References). Patching each one leaves the next one open, so the class is closed at the step boundary instead. Invariants 1 to 3 cover the tree, the commit and the facts a step hands on, invariant 4 covers what every payload says about itself, and field-level detail is left to the landing PRs (see Context). These invariants hold at every boundary, each is stated only here, and the decisions cite them by number.

1. **Clean tree at every step boundary.** Every step that can change files ends with the commit script (decision 12), whatever the step returned, so the next step starts on a clean tree at a known commit. A run starts only on a clean tree: dirty paths in the facts stop the run before planning, and the run never commits, stashes or discards an edit it did not make. Held by: the commit script refuses a dirty path outside the step's file list, and the branch and PR scripts refuse a dirty tree.
2. **A gate holds only for the commit it ended on.** A gate is a step whose pass the PR step depends on, such as the bump step, validation and local review today. Each gate holds only for the commit its step ended on, and the PR step needs every configured gate to hold for the commit it pushes. So any commit made after a gate, such as a validation fix round or a local-review fix, sends the run back through the gates it invalidates: every gate that ended on an earlier commit. Going back through the gates is bounded through `decide()` kind `gate_rerun`, and the run stops and asks at the bound. A gate that is not configured for the run, such as local review when the Codex plugin is absent, does not stop the PR step and does not count as held: it is listed on the PR with the run's decisions (decision 3). Held by: the workflow takes each step's end commit from the commit script's routing line and opens the PR only when every configured gate held on the same commit, and `push-branch.sh` takes that commit and refuses, in the same process as the push, when HEAD is another commit.
3. **Every planning pass starts from fresh facts.** The run enters planning only through the facts step: at the start, after `needs_replan`, and after a local-review escalation or root cluster. A replan sees the commits the run made and plans what is left, as a restart does (decision 2).
4. **Every payload says whether it is complete and which of its fields are external.** Each payload that crosses a step boundary, including the facts output the overlord passes to the planner on the current engine (decision 1), is checked against its schema. The schema marks each field that can carry external content, and each list or text that a producer may cut says whether it is complete or cut, with its full count when cut. A step refuses a cut field it depends on: the run stops before that step and names what was cut, so no step treats part of its input as all of it. External content crosses only under `plugin/governance/security-policy.md` (External Content Boundary and Injection-Suspect Classification); analysis-only already applies that boundary to its request (`plugin/workflow-src/analysis-only/main.js`). Held by: each payload's schema requires these labels, and a payload that fails its schema blocks the step that reads it.

Text: each step's preconditions and postconditions are rows of a contract table in `plugin/workflow-src/standard-delivery/contract.js` (amended 2026-10-24: the rows moved there from `main.js`, which keeps the checks they name; see Amendment 2026-10-24: short run messages), with a test for each row in `tests/workflow-scripts/`; each refusal is in its git script (decision 5); the `gate_rerun` kind is a row of `plugin/references/decision-autonomy-table.json` (invariant 2); and each payload's labels are in its schema, such as `plugin/references/facts-schema.json` and `plugin/references/plan-schema.json` (invariant 4). This ADR names the invariants and does not restate the rows. Lands in: PR2 (the script refusals and the facts schema), PR3 (invariant 4 for the facts the planner gets on the current engine and in analysis-only), PR4 (the plan schema), PR6 (the table, invariants 1, 3 and 4), PR7 (invariant 2, and the rows for the bump, validation, local review and PR steps).

Each hand-off in the outline is an obligation for the PRs in the last column: each covers it with a contract table row or a schema, and a test. The table says what the consumer needs, not how the code provides it, and invariant 4 holds on every row.

## Decision

Decisions 1 to 3 are the user's calls. Decisions 4 to 23 are journal items J1 to J20 of the slice plan. Decisions 24 and 25 come from the S11 surprises. Decision 26 and the step invariants come from the review of PR #419.

1. **The planner has no shell (call 1, option A).** Decided: cerebrate's `tools:` drops Bash and every `Bash(...)` entry. A facts step gives the planner what the shell gave it: branch state, the branch's history against trunk, and the text of any issue or PR the request names (outline step 1). That text is external content and reaches the planner only as invariant 4 allows. The planner reads files with Read and searches with Glob and Grep. It loses git research beyond the facts, such as `git blame`, the log of one path, and a file at an older revision. standard-delivery runs that step anyway. analysis-only gains a facts step. On the current engine, the overlord runs the facts skill and passes its output to the planner when it delegates, under invariant 4. Reason: the cerebrate tool-list finding below. Read-only becomes true by construction instead of by prompt, Glob and Grep come back (S11-c), and planner prompts drop to near zero. S11 surprise 3 backs it: any agent with Bash loses Glob and Grep. Text: `plugin/agents/cerebrate.md` (frontmatter, and the line that prefers Read, Glob and Grep), the CLAUDE.md line on read-only enforcement, a pin in `tests/policy/` that replaces the overclaimed rule in `safety-planner-no-write.json`, the new facts skill and `plugin/references/facts-schema.json`, `plugin/workflow-src/analysis-only/main.js`, `plugin/agents/overlord.md`. Lands in: PR2 (facts skill, script and schema), PR3 (the rest).
2. **No run record for standard-delivery (call 2, option A).** Decided: git and GitHub are the record: the working branch, its commits (decision 12), and the PR. A new session restarts the request. The planner plans what is left on the branch from the facts step's branch history (outline step 1) and the current files, which it reads with Read, and each git step checks for its own earlier effect (decision 5). When that history is complete, it gives the planner all a restart needs: the commits show which waves landed, the changed paths show what the branch did, including deletions and renames that Read cannot show, and the branch's PR shows whether the PR step ran. Dirty paths stop the run before planning (invariant 1), so edits cut off before their commit wait for the user, and a merged or closed PR on the branch stops the run too, as does a cut history (invariant 4). A replan inside a run reads the facts the same way (invariant 3). The facts carry no file contents from trunk, because what is left is judged against the files as they are now. A request that needs a file's trunk side, such as undoing part of the branch, becomes a plan step, and the worker reads that side with its own shell. The history comes from the branch the checkout is on. After step 3 that is the working branch, so a new session in the same checkout sees it; a session started on trunk sees no history and plans the whole request. A run that starts on a branch other than trunk delivers on that branch: the plan must name it, and the planner asks when the branch's history does not fit the request. This matches analysis-only (ADR-0036 decision 10). Reason: a second record duplicates durable state and can go stale; 35 of 37 fallback runs were on old definitions. Spike S9 is not needed. Text: `plugin/workflow-src/standard-delivery/main.js`. Lands in: PR6.
3. **Trust the planner's gate flags and show every taken decision (call 3, option A).** Decided: `decide()` keeps trusting the planner's irreversible, architectural and safety flags, as in slice 1, and a plan runs with no review stop. Every decision a run takes for the user is listed in the final message and in the PR body, or in a PR comment when the run reuses an open PR. One stop is added: the plan schema requires each step to declare any effect outside the repo, such as a deploy, a publish, a migration or other write to shared data, or a write to an outside service over the network. A plan that declares an irreversible one goes to the user before the first wave, through `decide()` kind `external_effect`, which asks at every level. A declared reversible effect is listed with the run's decisions. Reason: an effect inside the repo stays on the branch until the user merges, and the merge is the one irreversible step for it. The PR body puts every taken decision in front of the user at that step, and a branch change undoes one. An effect outside the repo happens during the waves, before the PR exists, so the PR comes too late for it, and a branch change cannot undo an irreversible one. A review stop on every plan would add stops the user does not want: in the usage research, 175 of 483 user prompts were approvals or continuations, and their root cause was planner questions that ended the run, not a missing plan review (`docs/research/2026-10-hivemind-usage-analysis.md`). An effect outside the repo that the plan does not declare is a recorded residual. Text: `plugin/workflow-src/lib/decide.js` (unchanged), the `external_effect` entry of `plugin/references/decision-autonomy-table.json`, the declaration in `plugin/references/plan-schema.json` and in the `plan:` block in `plugin/agents/cerebrate.md`, the stop before the first wave in `plugin/workflow-src/standard-delivery/main.js`, `plugin/workflow-src/lib/result.js`, the PR step in `plugin/workflow-src/standard-delivery/`, the open-plan-pr script under `plugin/skills/open-plan-pr/`. Lands in: PR4 (the plan schema), PR6 (cerebrate's plan block, the `external_effect` entry and the stop before the first wave), PR7 (the rest).

## Cerebrate tool-list finding

At runtime cerebrate has Read, WebSearch, WebFetch and Bash, and nothing else that matters here. Glob, Grep, LSP and the claude-mem tools are missing, and Bash is the whole tool.

Evidence:

- **Tool list.** Claude Code 2.1.304, cerebrate spawned through the Agent tool outside a workflow: Read, WebSearch, WebFetch, Bash and SubagentHandback. Spike S3 (2.1.302, a workflow agent) showed the same set plus StructuredOutput and advisor, so the finding is not specific to workflows.
- **Glob and Grep.** The tools reference (code.claude.com/docs/en/tools-reference, "Glob tool behavior") says that on macOS, Linux and WSL they are left out of the default tool set, and a subagent gets them back only when its `tools:` lists them and leaves out Bash. cerebrate's 28 `Bash(git ...)` and `Bash(gh ...)` entries count as Bash. S11-c and S11 surprise 3 confirm it.
- **LSP** stays inactive until a code-intelligence plugin is installed. The **claude-mem tools** are inherited MCP tools and are absent when claude-mem is not connected.
- **Bash is not scoped.** The sub-agents docs define no `Bash(...)` specifier for `tools:`. In smoke-414, smoke-602 and smoke-603, planner commands outside the patterns reached a normal permission prompt, not a refusal. S11-b confirmed it: an agent with `tools: Read, Bash(git status *)` had the whole Bash tool, and `touch` prompted.

What follows: the planner was read-only only because its prompt said so. The CLAUDE.md line "Read-only enforcement on cerebrate is done by restricting `tools:` list" is false as written. `tests/policy/safety-planner-no-write.json` pins only that Write and Edit are absent, so its rule "Planner cannot write files" claims more than it checks. cerebrate's line that prefers Read, Glob and Grep points at tools it does not have, so every search becomes a Bash call, the main source of planner prompts in manual mode (up to 19 per round in smoke-602). Decision 1 resolves all four.

## Consequences

**Positive**

- Delivery transitions cost no model turns. Fixed agent calls per run are facts, plan, branch, bump, validate, review and PR, plus a commit runner at the end of each step that can change files (decision 12); each wave adds its workers.
- Planner questions are decided or asked. Amended 2026-10-23: a delivery run that stops with questions still open ends blocked and names the next action, so complete always means a pull request exists (see Amendment 2026-10-23: question keys, blocked stops and the question template).
- Git hard stops and the checks for earlier effects are code, shared by both engines.
- No step hands the next one a dirty tree, a commit that skipped a configured gate, or a cut or unlabeled payload, and fetched issue and PR text reaches the planner only as external content (step invariants).
- The planner is read-only by construction, and its searches no longer prompt. Amended 2026-10-23 (issue 428): its Reads and Greps of plugin files outside the working folder skip the prompt only for a marketplace install in the default cache, in the turn that loads route-workflow or another skill with the `Read(~/.claude/plugins/cache/brenpike/hivemind/**)` entry. A resume turn, Agent-tool subagents on the state machine and other load locations still prompt (see Recorded residuals and Amendment 2026-10-23: skill allowed-tools file grants).
- Delivery keeps no state that can drift from git and GitHub.

**Negative or costs**

- A new session re-plans a paused delivery run, which takes a few minutes. A crash mid-step leaves uncommitted edits, and the next run stops on them before planning until the user commits, stashes or discards them (invariant 1).
- An under-flagged architectural choice still costs a round of rework.
- On the current engine, the overlord must run the facts skill and pass its output to the planner, and WebFetch covers only public GitHub.
- The planner loses git research beyond the facts, such as `git blame`, the log of one path, and a file at an older revision.
- In manual mode, each Skill call from a workflow agent prompts once unless a `Skill(...)` rule covers it.
- Users approve the workflow once per project, through "don't ask again".
- A wave that ends blocked is committed before the run stops, so the branch can hold a worker's partial edits. The run's message names that commit.
- Any commit after a gate runs the gates it invalidates again, up to the `gate_rerun` bound (invariant 2). Each validation fix round costs a fix, a commit runner, a bump check and a validation run, and one made after local review also costs another local review.
- The plan's one classification types every commit the workflow makes, so bump-type sees the plan's kind of change, not each step's.
- A branch whose history the facts cannot fully carry stops before planning (invariant 4). PR2a settled this: the facts are one complete file per run, no list is capped, and long text is chunked. The facts script checks every line of the file it writes against one bound, whatever field it holds, so each line fits one Read page. A chunk can be whitespace only (see the ADR-0036 amendment 2026-10-20). A cut arises only from a failed GitHub page or no merge-base, and both stop planning (see Deferred items).

## Risks

- **The relayed user message outranks runner tasks.** Decision 24 keeps the overlord's own text clean, but the user's request is relayed to every runner as written. A delivery request worded like "no changes", or one that names a git action, can make a runner skip or change its step. The workflow blocks when a script's routing line is missing or malformed, which catches a skipped git step, but not a drone that edits less than its task asks. The PR8 live smoke covered it once: under a request that ended "Make no other changes", every runner and worker ran its step (see PR8 live smoke). One session does not retire the risk. The resume case has the same root cause. The harness relays the user's resume reply to every agent the resumed run starts, and tells each one that the reply wins over its task. In issue 432, the user answered a planner question, and the branch step read that answer as an order to stop and returned blocked. The mitigation is the fixed sentence of decision 24: every later agent prompt except the planner's revise prompt says the reply was already applied and is not an instruction for that task. A sentence is a prompt, not a control, so a step can still refuse. Bounded impact: a step that still refuses stops the run as blocked, and the run's message shows the reason the step returned. Git writes go only through the committed scripts (decision 5), so a step that misreads the reply cannot write to git outside them. Link: https://github.com/brenpike/hivemind/issues/432.
- **Step text in a blocked message.** Step and script text reached the user-visible blocked message raw, and each site handled it differently. Local review findings 5b459198 and d460cb76 on this branch found it, under issue 432. A step reason could add lines, terminal escapes or bidi controls to the message. The fix is one encoder, `encodeUntrustedText` in `plugin/workflow-src/lib/result.js`. It JSON-encodes the value and writes every code unit outside printable ASCII as a `\u` escape. Reasons go through `quoteDiagnostic` and `describeReason`, which first make the value one line and cut it to 200 characters. Standard-delivery and analysis-only both use it. Tests allow `.blocker` and `.stderr` reads only in `describeReason`, `describeRelayBlocker` and `describeCommitBlocker`. Three residuals remain. (a) Markdown inside a quoted reason can still render inline. Bound: the reason is one quoted line after fixed text, so it cannot start a heading, a list or a new line. Rejected: escaping Markdown characters garbles paths and identifiers, and a code span around each value adds noise to every message. (b) Planner prose is shown as written: brief fields and verbatim text rendered by `plugin/workflow-src/lib/brief.js`, and the analysis-only report. Bound: the planner writes it for the user, GitHub text is scanned before planning, and it is display only. Rejected: the ASCII encoder would garble text the user must read, and issue 431 reworks that template. Annotated 2026-10-23: issue 431 reworked the template (see Amendment 2026-10-23: question keys, blocked stops and the question template). The residual stands, since brief fields still show as the planner wrote them. Amended 2026-10-24 (issue 445): verbatim text shows only for an ask the workflow marks exact, today an irreversible effect, under "Word for word:", so planner verbatim reaches a question only there (see Amendment 2026-10-24: short run messages). (c) Non-ASCII text in a reason shows as `\u` escapes. That readability cost is accepted for a closed allowlist: only printable ASCII passes as written. Link: https://github.com/brenpike/hivemind/issues/432.
- **Runners skip governance.** The haiku drone in S11-g read none of the governance docs its body says to load. Runner safety rests on the committed scripts, not on the drone's reading.
- **External text the scan does not catch.** The injection-suspect patterns are a list, so the text of a named issue or PR that matches none reaches the planner as data and can still shape the plan. The commit script refuses edits outside each step's files (decision 12), git writes go only through the scripts (decision 5), and every decision the run took is on the PR before the user merges (decision 3). An effect outside the repo does not wait for the PR: the plan must declare it, and an undeclared one is a recorded residual. Today the planner reads that text itself, under the boundary alone.
- ADR-0037 names text homes that do not exist yet, and the hand-off table can miss an obligation. Each landing PR's schemas, contract table rows and tests are the check (see Context). A later PR that changes a decision amends this ADR in the same PR.
- PR2 changes git skills the fallback uses. Their routing lines stay unchanged, their contracts change only by additions such as the optional expected commit for `push-branch.sh`, and tests cover both call paths.
- The spike facts are tied to Claude Code 2.1.304, and the PR8 live smoke facts to 2.1.308.

## Recorded residuals

- **An effect outside the repo that the plan does not declare (decision 3).** Root cause: workers have the whole Bash tool, since `tools:` cannot scope it (the cerebrate tool-list finding), and whether a step has an effect outside the repo, and whether that effect is reversible, is the planner's judgment, as its gate flags are. A worker's effect that the plan did not foresee, or a declared one the plan wrongly marks as reversible, runs during the waves, before the PR exists. Bounded impact: only the harness permission mode catches it. In manual mode the command prompts unless an allow rule covers it. In auto mode the classifier blocks actions it judges risky, though S12 shows it can accept one (decision 6). In bypass mode nothing catches it. Brood children start in bypass mode and stay on the current engine until slice 4 (decision 10), so neither this stop nor a prompt applies to them. The exposure is inherited: on the current engine, workers have the same shell, and a plan goes from planning to implementation with no stop. A step whose task is the effect, such as a deploy step, is in the plan and must be declared. A plan step's file list can name a path that is a symlink to a target outside the checkout, so a worker's edit there lands outside the repo; this is the same exposure, since workers already have the whole Bash tool, and it is the filesystem-alias residual recorded in `plugin/skills/next-wave/scripts/next-wave.sh`, whose rule `plugin/workflow-src/lib/waves.js` mirrors (local Codex review finding 5a089cde on PR6). Why the obvious fix was rejected: a deny or ask rule for deploy, publish, migration or network commands is a deny-list. Bash rules match the command as written, so another spelling or a wrapper script gets past them, and the list grows with each miss and differs per project (decision 6, call 3 B). A review stop on every plan is rejected in decision 3. Review thread: https://github.com/brenpike/hivemind/pull/419#discussion_r4321284654.
- **Raw push to trunk (decision 6).** Root cause: the harness has no control that stops a raw `git push origin HEAD:main`. Bash rules match the command as written, and the auto-mode classifier accepted that push from a workflow agent in S12, where it landed. Bounded impact: hivemind's own pushes go through `push-branch.sh`, which refuses trunk. Only an agent that steps outside its scripts can push to trunk, and server-side branch protection on the remote stops it there. A typed drone in S12 refused on its own, which helps but is not a control. Why the obvious fix was rejected: a deny or ask rule is a deny-list that `git -C . push` gets past.
- **A plugin update between pause and resume (decision 8).** Root cause: a resume by `name` runs the currently installed script, not the copy the run started with. Bounded impact: only when the plugin updates while a run is paused. Earlier agents are served from cache, and every git step checks for its own earlier effect (decision 5). Why the obvious fix was rejected: resume by `scriptPath` runs the stored copy, but it prompts on every resume and no rule covers it.
- **Plugin Reads outside the default plugin cache (decision 9).** Rewritten 2026-10-23 (issue 428; see Amendment 2026-10-23: skill allowed-tools file grants). Root cause: `${CLAUDE_PLUGIN_ROOT}` is substituted only in `allowed-tools` Bash rules, and a settings rule expands no `${...}` variable (ADR-0010's 2026-08-25 amendment), so the skill entry `Read(~/.claude/plugins/cache/brenpike/hivemind/**)` names the default cache folder of this repository's marketplace entry, not the folder `${CLAUDE_PLUGIN_ROOT}` resolves to. Bounded impact: when the plugin loads from anywhere else, such as `--plugin-dir`, a marketplace added from a local path, a plugin cache moved by `CLAUDE_CODE_PLUGIN_CACHE_DIR`, a plugin synced from claude.ai, or a fork under another marketplace name, no entry matches, and Reads and Greps of plugin files outside the working folder prompt in manual mode. Before this change, route-workflow's bare `Read` entry hid those Read prompts in the launch turn, because it approved every Read of every path for the rest of the turn, workflow agents included. The entry never approves a Read outside hivemind's own cache folder. Per-user remedy: a `Read(//<plugin folder>/**)` rule in the project's gitignored `.claude/settings.local.json`, the form S11-d passed. Why the obvious fixes were rejected: a bare `Read` grants every path, which is the defect issue 428 removes; a rule per load location is a list that grows with each location; and a per-machine rule goes stale at every plugin update (see Considered Options). Review thread: https://github.com/brenpike/hivemind/pull/419#discussion_r4320879672.
- **A trunk bump that lands after the facts step (decision 26).** Root cause: the bump step reads each artifact's version at the facts step's `trunk_commit`, and trunk can move between the facts fetch and the merge. Bounded impact: a trunk bump in that window leaves the branch with the version trunk already has. This is the same race at merge time that today's engine has. The version is shown on the PR, so the user sees it before the merge, and a later run or a rebase picks up the new trunk. Why the obvious fix was rejected: a second fetch before the push still races with a trunk bump that lands after it, and it adds a step.
- **Workflow-agent searches outside the working folder prompt (PR8 live smoke F2).** Rewritten 2026-10-23 (issue 428; see Amendment 2026-10-23: skill allowed-tools file grants). Root cause: a workflow agent's Read or Grep of a path outside the working folder prompts (`reasonCode: workingDir`) unless a rule or a skill grant covers it, and the plugin's governance files sit outside the consumer's working folder wherever the plugin loads from, a checkout or the plugin cache under `~/.claude/plugins/cache/`. The planner's agent file loads governance by path and searches it with Grep. Covered now: for a marketplace install, the turn that loads route-workflow, or any skill with the `Read(~/.claude/plugins/cache/brenpike/hivemind/**)` entry, pre-approves Read and Grep of plugin cache files for the workflow agents it launches, since a Read rule also applies to Grep (per the permissions docs; the 2026-10-23 headless test verified it, recorded in ADR-0010). Still prompting, inherited: a resume turn, where the main session loads no skill before it resumes the workflow by name; Agent-tool subagents on the state machine (untested); and the load locations outside the default cache in the residual above. Bounded impact: one prompt per such search, in manual and in auto mode, and the run waits for the answer: an unattended auto run waited 1h54m in the PR8 live smoke. Nothing runs past the prompt without the user's answer, and an answer for the session covers the path from then on. The condition is inherited: the planner loads and searches the same governance files by path on the current engine, and ADR-0036 decision 11 recorded planner prompts for the plugin's own governance files before slice 2. Why the obvious fixes were rejected: a bare `Read` or `Grep` skill grant approves every path (issue 428); a seeded rule can never be withdrawn, because the merge never removes an entry; a per-machine rule goes stale at each plugin update; and delivering governance as skill text or script data changes every agent and the current engine (see Considered Options, J6). A prompt rule telling the planner not to search plugin files would be a promise, not a control. Links: https://github.com/brenpike/hivemind/issues/428, `~/code/hivemind-workflow-spikes/pr8/delivery/rerun/results-rerun.md` (F2).
- **A routing line printed on the state-machine path (smoke-603 N2, PR8 live smoke).** Root cause: on the state machine, the overlord writes its own text between many bookkeeping tool calls. In one PR8 smoke session, right after a `silent_turn_reminder` from the harness, it printed "Route: exploratory (no commit/PR excludes delivery)", against the `plugin/agents/overlord.md` (`## Engine`) rule that keeps the routing outcome out of chat. The script path has no such turns, and no script-path session printed it (decision 21). Bounded impact: the inherited engine only, one line once in the smoke, with no secret in it and no step changed. Why the obvious fix was rejected: another prompt rule restates the one that the model broke here, and the state machine retires in slice 5. Links: `~/code/hivemind-workflow-spikes/pr8/delivery/results-delivery.md` (item 2d), https://github.com/brenpike/hivemind/issues/409#issuecomment-6281012540 (smoke-603).
- **Open questions recorded as complete on the current engine (smoke-603 N1).** Root cause: the fallback's `analyze` state maps open questions to blocked, while the overlord in one of three sessions recorded `complete` and listed the questions, as the script engine would. The two engines disagree on this case. Bounded impact: current engine only, low severity, and the questions were shown to the user. Why the obvious fix was rejected: rebuilding `decide()` in fallback prose is what failed in #408, and the fallback retires in slice 5.
- **Made-up inputs-file tokens (smoke-603 N4).** Root cause: the overlord writes the inputs-file token itself, with a fixed fake timestamp and a low-entropy suffix, while the skill relies on it for per-invocation uniqueness (ADR-0019). Bounded impact: current engine only, and it matters only with two concurrent overlords in one checkout. Why the obvious fix was rejected: it costs one extra tool call per transition, and the code retires in slice 5.
- **Scan coverage relies on the facts runner's count (invariant 4).** Root cause: a workflow script cannot read files, so analysis-only decides whether to run the injection scan, and checks that the scan returned one result per `text_id`, from the `external_texts` count and ids that the facts runner relays from `gather-facts`. If the runner miscopies the count or skips an id, GitHub text can reach the planner unscanned. On the current engine the overlord counts the scan results itself, by judgment. Every check tried moves trust from one model's report to another's. Bounded impact: the facts runner never reads GitHub text itself, the scan runner gains nothing by under-reporting, and the planner has no shell, Write or Edit tools (decision 1), so unscanned text can shape a plan only as data. The commit script, git-writes-only-through-scripts and the PR showing every taken decision (decisions 3, 5, 12) still apply. The exposure is no worse than before this change, when the planner read that text itself under the boundary alone. Why the obvious fix was rejected: a check value printed by `gather-facts` and recomputed by the workflow (a hash over the routing values and content-bound ids) closes honest copy errors, but adds a hash kept in step between jq and JS, new id formats and test rewrites, and still trusts the runners against deliberate forgery. Its cost outweighs the bounded impact here. Hardening, if any, moves to PR6, where the shared lib holds the check: https://github.com/brenpike/hivemind/issues/409. standard-delivery's facts step relays `gather-facts` stdout too. The workflow parses that relay with the script's routing spec and re-checks it for consistency in code. The shared check lives in `plugin/workflow-src/lib/facts.js`. A forged relay of `external_texts`, `cut`, `delivery` or `delivery_stops` that is still consistent is the same bounded residual. No check value is added. Review findings: Codex local review findings 112d4411 and b94aaa9c on PR3.

smoke-603 N3 (the planner tries to run scripts) is not a residual: decision 1 removes the shell.

## Amendment 2026-10-23: question keys, blocked stops and the question template

This amendment covers issues 433, 434 and 431, under epic 435. It updates three places in place: the Consequences line on planner questions, the deferred item on delivery-tail questions, and Risks residual (b). ADR-0036 gains a matching amendment for its decisions 7 and 16. The rest of ADR-0037 is unchanged.

- **Every question key is derived from its kind, a scope and the text shown (issue 433).** Root cause: a key built per call site from a hand-picked subset of fields. It was too narrow for local review findings 7578f16f and 0c804e49, and too wide for issue 433. Plan acceptance was keyed on the plan summary, which the planner's revise step rewrites when it records the reply, so the settled question was asked again until the pause limit. Decided: every question key is derived in `resolveDecision` from three parts: its kind; a scope; and the exact text `renderQuestions` shows. The scope is the pass for most kinds, the pass and the whole plan for both plan acceptances, and the run for `trunk_stale` and `external_effect`. Plan acceptance is asked only when no other question of the pass is open. A reply that settles it runs the plan result it showed, never the revise output. Eliminated class: no field list exists, so an answer cannot carry over to a question shown with other text, and a rewrite the user cannot see cannot re-ask it. The key binds what a question shows, not everything a plan does: the plan acceptance question shows the plan summary as its verbatim text, so a settled acceptance runs the whole plan result it was shown with (see the residual on plan acceptance below). Rejected: a field-subset key (complete-the-known-set), a plan digest compared with the adopted revise output (a summary rewrite re-asks, issue 433), and a prompt rule, which is a promise, not a control. Text: `resolveDecision`, `resolvePlanAsks` and `runPlanningPass` in `plugin/workflow-src/standard-delivery/main.js`, rows SD-09 and SD-52.
- **Planner questions get a key.** A planner question is keyed like every other question: its kind, the pass, and the exact text `renderQuestions` shows for it. Consequences: a settled planner question raised again with any visible change is asked again, within the pause limit, and at the limit the run ends blocked (below). An accept reply that also asks for a change runs the plan as shown. Acceptance can cost one more pause when other questions are open. Rejected: a key on the brief id, which the model writes, or on a label like Q1, which moves with the order of the questions.
- **Residual: plan acceptance shows the summary, not the plan.** Amended 2026-10-24 (issue 445): the question no longer shows the summary. Root cause: `buildPlanAcceptanceBrief` has shown `plan.summary` as its verbatim text since PR8 (D1), so the user approves the summary while the run executes the plan's steps, files, branch, versioning and reversible effects. Local review finding 8fe07586 on this branch raised it. Inherited: this amendment changes only the key and which plan result runs, the one shown, never what the question shows. Bounded impact: at the default autonomy level `plan_acceptance` is taken and never shown, and `remediation_plan_acceptance` always asks. Either way the steps run only on the working branch, the commit script commits only each step's files (decision 12), every irreversible effect is asked on its own with its exact text (row SD-11), and the reversible effects and every taken decision are in the final message and on the PR before the user merges (decision 3). Rejected: showing the whole plan in the question. A multi-step plan competes with the question for the pause message size budget (`plugin/workflow-src/lib/result.js`), so a compact form would cut the text the user approves, it undoes the ask-first template of issue 431, and at the default level no acceptance question is shown at all, so it is not the approval boundary. Link: https://github.com/brenpike/hivemind/issues/433.

Reason: the user approves an irreversible effect word for word, so a changed text is a new question the user must approve (decision 3). Asking it again is the intent, not the bug. Text: `resolveExternalEffects` in `plugin/workflow-src/standard-delivery/main.js`, row SD-11.
- **A delivery run that stops with questions open ends blocked (issue 434).** Before, a run that reached the pause limit, held replies too long to carry, had an exact question too long to show whole, or asked after the last wave (stop reason `before_pr`) ended complete with the questions listed, so complete did not mean a pull request existed. When the run made commits, it names the branch and says the new run plans what is left from the commits on it, and at a `before_pr` stop it also says the pull request can be opened from those commits. Amended 2026-10-23 (issue 444): the `before_pr` line no longer offers a pull request, because a gate may not have held on those commits. Only the PR step ends complete, so complete always means a pull request exists. analysis-only is out of scope and still completes (ADR-0036 amendment 2026-10-23). ## Amendment 2026-10-23: local review holds the pull request on every path (issue 444)

This amendment covers https://github.com/brenpike/hivemind/issues/444, under epic https://github.com/brenpike/hivemind/issues/442. It updates one place in place, with a dated note: the issue 434 bullet of the amendment on question keys, blocked stops and the question template. The rest of ADR-0037 is unchanged.

- **Root cause.** The rule for which local review exits hold the gate before a pull request lived only inside the two engines: `localReviewRoutes()` in the workflow script and the `local_review` transitions in `plugin/workflows/standard-delivery.json`. A path outside both read its PR preconditions from workflow.md (PR Requirements) and the open-plan-pr checklist. Both named validation and the version bump, but not local review. The issue 428 run shows the effect. Its delivery tail stopped blocked, and the overlord finished the tail by hand. It ran the local reviewer with an iteration limit of 1, which no rule allowed. The reviewer fixed a high-severity finding in that round and returned `max-iterations-reached`. The overlord took that exit as a pass and opened PR 443, so the fix reached the pull request unreviewed. Also, at a `before_pr` stop the script's own next-action line said the pull request can be opened from those commits, even when a gate had not held on them. The state machine also sent `diminishing-returns` straight from `local_review` to `open_pr`, so an advisory nobody took could open the pull request.
- **One home for the gate rule.** workflow.md (PR Requirements) is the one statement of which local review exits hold the gate and which hold nothing. Other text points to it and does not restate it (P20). The open-plan-pr checklist checks it, and its stop list names it. Rejected: a copy of the exit list in each consumer, since a second copy drifts (P22).
- **The `before_pr` line no longer offers a pull request.** It says no pull request opens until every gate holds on those commits.
- **The reviewer limit is fixed at 10.** The local reviewer's iteration limit is always the `max_iterations` value of its Input Contract. A delegation that asks for any other limit, under any key name, ends blocked at initialize. Before, a caller could lower the limit with no rule allowing it, so `max-iterations-reached` could follow a single round.
- **Diminishing returns follows the two-round rule.** The reviewer honors a `diminishing-returns` verdict only when the fix-ledger shows this iteration and the one before it each found only unusual-setup edge cases or wording findings. A finding that needed a real fix resets the count. So the exit never fires at iteration 1, and never right after a real fix made in the same round.
- **Diminishing returns waits for a decision on the state machine.** `local_review` sends `diminishing-returns` to the overlord decision state `diminishing_returns_decision`, which the `diminishing_returns_exit` row of `plugin/references/decision-autonomy-table.json` resolves. Only its `taken` outcome reaches `open_pr`. `not_taken` and `blocked` end the run at `blocked`, before the pull request, as an ask does on the script (SD-38). The definition moves from version 3 to version 4, so a run resumed from version 3 meets the version-skew doors. Rejected: keeping the direct route and recording the state-machine path as a judgment residual, because a declarative state closes it. Rejected: sending `not_taken` back to `local_review` or to `review_remediation_plan`, because a terminal route cannot reach the pull request or loop, and it matches the script.
- **Eliminated class.** A pull request opened from commits whose local review did not hold the gate, on any path that reads workflow.md: the workflow script, the state machine, or a step taken by hand. A test fails when the script table, the state machine or the workflow.md statement disagree. The only state-machine transitions into `open_pr` are `local_review` `clean`, `diminishing_returns_decision` `taken` and `local_review_decision` `skipped`, and a test fails on any other.
- **Text homes.** `plugin/governance/workflow.md` (PR Requirements). `plugin/skills/open-plan-pr/SKILL.md` (the checklist and the stop list). `plugin/agents/local-reviewer.md` (The Loop, steps 1 and 9). `nextActionLine` and `localReviewRoutes` in `plugin/workflow-src/standard-delivery/main.js`, rows SD-23 and SD-35. `plugin/workflows/standard-delivery.json` (`local_review` and `diminishing_returns_decision`). The `diminishing_returns_exit` row of `plugin/references/decision-autonomy-table.json`. The policy fixture `tests/policy/safety-pr-requires-local-review.json` pins the workflow.md statement and its consumers.
- **Residual: the hand path stays a judgment path.** Root cause: review questions in the delivery tail have no reply path on the script, so a blocked tail can still be finished by hand. That path is gated by workflow.md and the open-plan-pr checklist, which a model reads and follows. They are not a control the script enforces. Bounded impact: every pull request is in front of the user before merge. The residual goes away when https://github.com/brenpike/hivemind/issues/441 gives review questions a reply path on the script.

Links: https://github.com/brenpike/hivemind/issues/444, https://github.com/brenpike/hivemind/issues/441, https://github.com/brenpike/hivemind/issues/442.
