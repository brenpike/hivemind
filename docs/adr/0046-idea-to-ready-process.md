## Context

The Lair (ADR-0045) delivers only Ready Issues, unattended. Today `readiness:ready` is a rubric judgment applied in triage, with no artifact behind it and no check a machine can repeat. On the Lair initiative, two adversarial design reviews found 3 critical and 6 high gaps that the diff-based reviews missed. Gaps left in a design become blocked steps, replans and parks inside factory runs.

There is also no guided path from an idea to a ready issue, and a half-finished initiative leaves no trace of where it stopped.

The [PRD](../prds/idea-to-ready.md) sets the WHAT. The [solution design](../initiatives/idea-to-ready/solution-design.md) sets the HOW. This ADR records the process decisions from that design that are hard to reverse. The Abathur council, first drafted with this design, moved to its own initiative, #638.

## Decision

### Tracks and readiness

1. **Two tracks.** The initiative track is for features, epics and any change to a public contract or governance semantics: capture, interrogation, PRD, the UI prototype when the PRD's `**UI:**` line says `yes` (decision 12), solution design and ADRs, design review, docs merge, slicing, triage, then a handoff check. The standalone track is for bugs, chores, docs and small refactors: an issue carrying a spec block, then triage. The spec block is `## Problem`, `## Evidence`, `## Acceptance Criteria`, `## Scope boundary` and `## Open questions`. Each is non-empty, Acceptance Criteria holds at least one `- [ ]` or `- [x]` item, and Open questions reads exactly `None`.
2. **The track is a script-readable fact.** It is read, never judged.
   - An issue with a native parent is an initiative slice. Any other issue is standalone.
   - The parent must carry `type:epic`, else the slice fails `parent_not_epic`.
   - A standalone issue whose `type:` label is not `bug`, `chore`, `documentation`, `refactor` or `enhancement`, or whose `effort:` label is `l` or `xl`, fails with a promote reason.
   - The type and effort labels are human-confirmed, because triage applies them only after its confirm gate.
3. **One deterministic readiness check, three callers.** Triage, the guide's handoff check and Lair admission share one check. Lair admission is ADR-0045 decision 10, as amended by #625.
   - The check is one shell library, `plugin/skills/_shared/readiness-check.sh`, sourced by each caller's own script, so no skill calls another's script.
   - It checks structure, existence, versions and labels, never quality. It writes nothing.
   - It reads issues through `gh`, except in snapshot mode: given a recorded issue snapshot and a trunk commit, it makes no GitHub read of its own, and its GitHub inputs are exactly the snapshot's fields. Lair admission calls it in snapshot mode; triage and the guide read through `gh`.
   - Each caller fetches and passes the remote trunk commit id, never a branch name or local ref. The check rejects a value not matching `^[0-9a-f]{40}$` or `^[0-9a-f]{64}$` before any git call. The Lair passes the trunk commit of the claim's snapshot, the commit a first claim spawns its strain from. For a re-claim it passes the snapshot's trunk commit, never the parked head it spawns the strain from.
   - **Document existence test.** Every git read of an initiative document, by the check, verify, stage derivation, the stamps and the slicing refusal, goes through one test, implemented once in this library: a document exists at a commit only as a regular file blob, a symlink, submodule or tree reads as missing, and a document's blob id and content are read only from that entry ([solution design](../initiatives/idea-to-ready/solution-design.md), Document existence test).
   - Design and record links bind to the slug of the parent epic's seed marker, never read from the issue. An epic without a valid marker fails `epic_marker_missing`, and a link to another slug fails `design_slug_mismatch`. The PRD path is derived as `docs/prds/<slug>.md`, never read from the issue. Every path passes a fixed allowlist before any git call. Reason codes carry line indexes, never issue text. A slice of an initiative whose PRD says `**UI:** yes` also links its UI prototype, whose structure and existence the check judges, never its quality (decision 12).
   - It returns one JSON line per issue naming the evaluated commit, with a track, a result and reason codes from a closed set. A missing document is a reason code. Only an unresolvable commit or a failed `gh` or `git` process exits non-zero.
   - A read where any `pageInfo.hasNextPage` is true is truncated and exits non-zero. Callers discard every line of a run that exits non-zero, and none treats it as a pass.
4. **Ready may carry open blockers.** A passing slice is proposed ready even with open blocked-by links. `readiness:blocked` is kept only for a block with no issue link. Ready Issue keeps its rule: a slice is claimable only once no blocked-by dependency is open.
   - Each `#<n>` ref in a slice's Dependencies section needs its native blocked-by edge, else `dependency_edge_missing:<n>`.
   - Triage runs the check on every issue it would propose as `readiness:ready`, with an overlay of the labels and edges its apply would write. A failing issue never enters the apply set as ready.
   - At apply, triage writes the ratings and edges first, re-runs the check with an overlay holding exactly `readiness:ready`, every other family and edge read live, and applies `readiness:ready` only to issues that still pass.
   - **Ready label authority.** The authorization is write permission on the latest `readiness:ready` labeled event, with the title and body unedited since (ADR-0045 decision 10, as amended by #625). The handoff check verifies it. "Maintainer" names a role, and triage's confirm gate is not an authorization boundary.

### Design artifacts and review

5. **Per-initiative docs folder.** `docs/initiatives/<slug>/` holds `solution-design.md`, `review-record.md` and, for an initiative whose PRD says `**UI:** yes`, `prototype/index.html` and `prototype/notes.md` (decision 12), with the same slug as `docs/prds/<slug>.md`. The PRD stays in `docs/prds/`. ADRs stay global and numbered in `docs/adr/`.
6. **Design review shape.** Each round's cerebrate pass is a fresh, read-only analysis pass with `Memory context: none`, run from the main session.
   - Each round is one fresh pass covering every angle: code truth, conflicts with the project's documented principles, governance and ADR conflicts, existing-path coverage, failure modes, trust and injection, and testability. Round 1 covers the whole documents; each later, confirming round reviews only the change since the previous round's reviewed commit and the fixes to its findings.
   - **UI prototype.** For an initiative whose PRD says `**UI:** yes`, every round also covers the UI prototype, both files, and checks the solution design against it. The exit rule and the three-round cap are unchanged.
   - When the design touches a trust boundary, credentials or the merge path, the round adds one pass by the configured local review tool, run through `hivemind:adaptation-cycle`; with none configured it is skipped and the record says so. A second model is used only when configured, never required.
   - The cerebrate pass's model is configurable (`HIVEMIND_DESIGN_REVIEW_MODEL`); a model the maintainer cannot reach falls back to cerebrate's own, and the record names each pass's reviewer and model. The local review tool's model is its own default, which hivemind never names ([ADR-0042](0042-tool-neutral-local-review.md) decision 7).
   - Before each pass the guide fetches the docs pull request, confirms the checkout is clean at its head commit and records that commit id, and the pass reviews that commit.
   - A pass that errors, times out or returns unparseable output yields no round and is re-run. A round is clean only when every completed pass of it raises no new finding and finds no earlier finding unfixed.
   - **Findings land before the next round.** Each finding of a round is fixed in the solution design, the PRD, an ADR or the UI prototype in the same pull request, or gets a `deferred`, `recorded` or `rejected` disposition with its reason, before the next round runs.
   - **Exit rule:** the review exits only with every open count (critical, high, medium and low) at 0 and one clean round, so a passing review has two or three rounds.
   - **Three-round cap:** a review that has not converged after round 3 stops and reaches the maintainer as a signal to split the initiative, and the initiative is split before its docs merge.
   - Every finding gets exactly one disposition: `fixed`, `rejected` with its reason, `deferred` or `recorded`. Critical and high findings are only `fixed` or `rejected`.
   - The record is rewritten after every round, and a lost session resumes from its rounds.
   - **Review fix.** Each round's fixes and its record rewrite land in one standard-delivery run, the record wave last. The run that writes `verdict` `pass` launches with local review off. A review fix to a stamped document after exit runs in this order:
     1. The guide returns the pull request to draft.
     2. One run lands the fix and a record wave that sets `verdict` to `fail`.
     3. One fresh confirming round runs over the diff since the stamps. It changes no `rounds` count and does not count toward the cap. A new finding makes it a re-review.
     4. With no new finding and no earlier finding unfixed, a record-only run with local review off re-stamps, to the commit that pass reviewed.
   - **Diminishing-returns check.** After every round, before the next, the review reads the record's Findings for diminishing returns, using its own three signals, modeled on the fix-ledger signals of `hivemind:detect-remediation-signals` but run whatever the severity of the open findings: recurrence on a surface already fixed; severity and reach trending down while fixes add surface; new findings that are edge cases an existing safeguard already bounds. When a signal fires, it surfaces to the maintainer unprompted with the options to narrow the claim and hand the rest to the slice that builds it, accept the rest as recorded residuals, or keep going. The options stay within the disposition rule: a critical or high finding is fixed, including by removing the claim it attacks, or rejected; only medium and low findings may be deferred or recorded. The maintainer decides, and the check changes neither the pass rule nor the round cap. The record lists each advisory and the answer (the user's direction after re-review round 4).
   - **Re-review after an amendment.** Rounds count from 1. The front matter is reset: `verdict` `fail`, `rounds` 0, every open count 0 and `clean_round` `false`; the stamps are kept. The earlier Rounds and Findings move under a dated History section. A re-review covers the whole documents when no record has passed.
7. **Review record contract.** The record starts with fixed front matter, which is the only part the readiness check parses: `stamps` (each a `path` and a `blob`), `verdict`, `open` counts by severity, `rounds` and `clean_round`.
   - **Blob stamps.** Each `blob` is the blob id the document existence test (decision 3) reads at the reviewed commit, read by the guide's script through the readiness check library and written by the record step as the guide names it, where the reviewed commit is the pull request head commit id the guide recorded before a pass, and matches `^[0-9a-f]{40}$` or `^[0-9a-f]{64}$`. The first record of a review stamps the commit round 1 reviewed. A record written with `verdict` `fail` keeps its stamps. Only the record that sets `verdict` `pass` re-stamps, to the commit its clean pass reviewed, so any change to a stamped document after that pass fails verify's stamp equality at the head. A passing record's stamps include the PRD, the solution design, for an initiative whose PRD says `**UI:** yes` both UI prototype files, and every ADR its own docs pull request adds or edits, never an ADR it only cites; a failing record keeps its stamps and may omit an ADR added after them.
   - **Stamp paths.** Each stamp path has one shape of the path allowlist: the PRD, the solution design, an ADR, or exactly `docs/initiatives/<slug>/prototype/index.html` or `docs/initiatives/<slug>/prototype/notes.md`, never a directory prefix. A stamp path outside them makes the record malformed (`record_malformed`).
   - **Pass.** The record passes when `verdict` is `pass`, every open count (critical, high, medium and low) is 0, `clean_round` is `true` and `rounds` is 2 to 3.
   - **Open counts.** Each severity's count is its findings with disposition `open`. Any critical or high whose disposition is not `fixed` or `rejected` counts as open.
   - **Staleness.** The record is stale when any stamped path's blob id at the passed trunk commit, read by the document existence test (decision 3), differs from its blob, or the path fails that test. A blob id is a content hash, so the merge method does not matter. Any edit to a stamped file makes the record stale until a review of the change re-stamps it.
   - **Verify.** The body holds a fixed Findings table. The design review skill's verify checks the front matter, the stamps and the table, and prints one `record-verify-failed: <record path>` line per failing record.
     - Every record the pull request adds or edits gets every check, whether or not its design is delivered. Each `deferred` Findings row's Note holds a `#<n>` issue reference, checked by shape only, with no `gh` call. Each `recorded` row's Note holds a repository path, a Markdown link target read relative to the record's folder or a code span read relative to the repository root, naming a file present at the pull request head. Verify reads every path, stamped or named in a Note, through the document existence test (decision 3). Every other passing record whose design is not delivered gets stamp equality only. Stamp equality and ADR inclusion are checked only for a record whose `verdict` is `pass`, and ADR inclusion only for a record the pull request adds or edits. It also fails a record the pull request adds or edits whose stamped PRD lacks a valid `**UI:**` line, and a passing record of an initiative whose PRD says `**UI:** yes` that does not stamp both UI prototype files (decision 12).
     - The guide runs it before the pull request leaves draft, in any repository.
     - **Draft until pass.** The guide keeps the docs pull request a draft until verify passes at its head and the record passes the pass rule, and neither GitHub nor `plugin/skills/github-review-loop/scripts/merge-approved.sh` under `HIVEMIND_AUTO_MERGE` ([ADR-0044](0044-settled-approval-and-opt-in-auto-merge.md)) merges a draft. A human who marks it ready and merges it, or a push after it is ready that `merge-approved.sh` then merges, is a recorded residual (Residuals). The draft rule meets the PRD's rule that a record with an open finding or a failed verdict cannot merge (#641) only while the docs pull request is a draft, which the guide keeps it until verify passes at its head and the record passes: while it is a draft, no merge path merges it, neither GitHub nor `merge-approved.sh`. After it is ready, a human merge or a `merge-approved.sh` merge of a later push can still merge a failing or stale record (the recorded residual), so the PRD's full guarantee is delivered by #619's own design of merge-time enforcement (asked after re-review round 4, answer Q25 A).
     - **Verify in CI is optional.** A repository may add verify to its own CI or validation as an optional capability, never required. This repository does, through `tools/validate.sh`, which maps `docs/initiatives/`, `docs/prds/` and `docs/adr/` to it. A repository without it keeps the guide's verify before ready, the readiness check and the fix-round commit refusal.
     - A verify failure is never fixed in place. Where a run's validation runs verify, the validate step reads only verify's integrity line in code and stops the run blocked, naming the record, before any fix decision, so no fix round runs. This narrows ADR-0037 decision 16 (answer Q13 A).
   - **Authority.** A record is authoritative only through a human-reviewed merge. Only the design review's record step, a drone with exact file scope, writes or re-stamps it. `runCommitStep` refuses a review record path, compared case-insensitively, in every validation fix-round commit of standard-delivery and pr-feedback-remediation and in every pr-feedback-remediation wave commit, a terminal stop naming it. Only a standard-delivery wave, the record step's path, may carry one. Other commit paths are bound by prose (Residuals). #605 builds `docs/prds/`, `docs/initiatives/` and `docs/adr/` into the Lair's auto-tier floor ([Lair design](../initiatives/autonomous-ready-issue-loop/solution-design.md), Component "Merge lane and auto tier"), not #623, so a docs pull request never takes the Lair's auto tier in any consumer project.
   - The record ships in the same pull request as the design, whose draft rule is decision 10.
8. **Design-decision rule.** Review Calls in the autonomy governance gains a rule for the design stages. A decision with a strong recommendation is taken and listed for veto in the review record and in a docs pull request comment the guide posts with `gh pr comment`, whatever it touches: PRD scope or acceptance criteria, an amendment of an accepted ADR, a trust-boundary, credential or merge-path change. Of design decisions, only two kinds are asked: a decision whose recommendation is weak or absent, and an action that is irreversible now, outside the unmerged pull request (for example closing or deleting an issue, publishing, a push to trunk). The asks other rules set (Tier A, Surface-Growth Escalation, the UI prototype approval gate of decision 12 and the diminishing-returns advisory of decision 6) are unchanged.
   - A decision with a weak recommendation or none is asked, never deferred; #638 may change this only by its own ADR. This amends ADR-0026 decision 2 for design-stage decisions only (answer Q16 A).
   - The design-decision gate reads Promotion Gate clause 1, irreversible, only, applied to the action taken now, not to what the design proposes. Clauses 2 and 3 are not read for design-stage decisions, because a design proposes changes and performs none. This narrows ADR-0026 decision 3 for design-stage decisions only (previously narrowed by answer Q18 A).
   - The design stages run no `decide()`. Take or ask is the conductor's judgment. The review record lists each taken decision with its recommendation strength and what it touches (scope, ADR amendment, trust, credential, merge path), so the maintainer can veto at merge. The confirming pass checks that each taken decision had a strong recommendation and took no irreversible action. A taken decision with a weak or absent recommendation is a finding (#619).
   - **UI prototype approval.** The maintainer's approval of an initiative's UI prototype, given as the answer to the guide's ask and recorded under Decisions asked in the review record, is the UI prototype stage's approval gate (decision 12). The `## Verdict` section in its notes only marks progress for stage derivation and authorizes nothing; the approval's authority is that answer, the record's stamps over both prototype files and the human-reviewed merge of the docs pull request. The guide asks for it beside the two kinds above. It is a stage gate, not a design decision with a recommendation, so the take-or-ask rule is otherwise unchanged. A UI choice inside the prototype with a strong recommendation is taken and listed for veto like any design decision. Added by the amendment of 2026-11-22, UI prototype stage and Lair corrections.
9. **A delivered design is frozen.** When every slice is done, the solution design gains `**Status:** delivered` and an `## As-built deltas` section in one docs pull request, and is never maintained afterward. The truth then lives in code, ADRs, the glossary and governance. Stage derivation reads `**Status:** delivered` before record staleness, and a delivered design's record is never re-stamped. A design is delivered when the first non-blank line after its title is exactly `**Status:** delivered`. Its slices then fail the readiness check with `design_delivered`, and verify skips its unedited record.

### Conductor and writers

10. **The guide is a user-only conductor skill with no stored progress state.** It runs in the main session with `disable-model-invocation: true`.
    - It is an orchestrator that owns the coupling, within ADR-0013's carve-out. It invokes the leaf skills by intent, and they stay uncoupled from each other.
    - No progress state or pointer is stored anywhere. The stage is a pure function of GitHub and git: the latest stage whose evidence exists. Evidence that does not resolve to one answer is reported as ambiguous and asked, never guessed.
    - It never applies `readiness:ready`. At the triage stage it sends the maintainer to `/hivemind:triage-backlog`, which is user-only.
    - **Docs branch.** Before stage 2 writes any tracked file, it creates `docs/<slug>` from the fetched trunk. It commits the stage-2 and stage-3 outputs through `hivemind:molt`, so the tree is clean for the first docs-branch run, at stage 4 when the PRD says `**UI:** yes` and at stage 5 otherwise. Every docs-branch standard-delivery run launches with draft true and no launch reference it could close: its one launch reference, once the docs pull request exists, is that pull request's number, because a closing line closes only issues and a reused pull request keeps its body. The first, the UI prototype build run when the PRD says `**UI:** yes` and else the first solution design run, opens the draft pull request, and later runs reuse it. The pull request leaves draft only after verify passes at its head and the record passes the pass rule. Before launching a run on a docs pull request that is not a draft, the guide returns it to draft with `gh pr ready --undo`. A push the guide did not launch is caught by the guide's verify before ready and the readiness check, and by verify in the repository's own CI where it adds it.
    - The seed issue carries a fixed marker line, and its author has write permission. The marker slug must match `^[a-z0-9]+(-[a-z0-9]+)*$` before any git or `gh` use, else the issue is ignored and named. The epic keeps the marker. Epics created before the guide gain it in #615's delivery, which adds it by hand to epics #603 and #614 before the readiness check is first used to label any slice ready. Until then their slices fail `epic_marker_missing`.
    - **Guide runs.** Each standard-delivery run the guide launches takes a request in a fixed layout: line 1 exactly `hivemind-guide-run: <slug>`; line 2 exactly `Docs pull request: #<n>` once the docs pull request exists, else `Docs pull request: none`; then the guide's fixed wording; then the maintainer's own words. No review text enters the request. The guide posts each round's findings, and review text it routes that is not already on the pull request, as conversation comments on the docs pull request with `gh pr comment`, under the executing user's credentials. The overlord takes `references` only from line 2, so the run's one launch reference is the docs pull request, and `hivemind:gather-facts` carries its body and conversation comments under the pass scan, which ends the run on a flagged comment. No issue number is ever a launch reference.
    - **A failed guide run returns to the guide.** A run the guide launched that fails or ends blocked returns to the guide, which re-derives the stage, with no Instinct takeover. The overlord tells such a run by the marker line that opens its request. This narrows ADR-0039 decision 4 for guide-launched runs (asked in re-review round 1, answer Q19 A). A refused or blocked launch starts no run and still runs on Instinct under ADR-0039 decision 3.
    - Only same-repository pull request heads and authors with write permission count. Ignored issues and pull requests are named in the report.
    - **Concurrent sessions.** A non-fast-forward push or a second docs pull request stops the later session, which re-derives its stage.
    - Note 2026-11-22 (ADR-0048 decision 8): 'a refused or blocked launch starts no run and still runs on Instinct' now rests on ADR-0048's one fallback, which covers every workflow.
11. **A drone with exact file scope writes design artifacts.** Solution designs, review records and design-stage ADRs are written by a drone with exact file scope, in a standard-delivery run on the docs branch. The design review's record step is the only writer and re-stamper of review records. The writer exception of `hivemind:plan-interrogation` is not extended: it stays the glossary and ADR writer during interrogation only. The UI prototype's `index.html` is the one exception: a changeling with exact file scope writes it in a standard-delivery wave on the docs branch, because presentational UI is its domain. #622 gives `plugin/agents/changeling.md` a scoped carve-out for `docs/initiatives/<slug>/prototype/index.html` only: it may carry the `?variant=` switcher, the ←/→ key cycling and in-memory stub state; the 3 to 5 variants are the intended alternatives, and the maintainer's verdict settles the visual decisions. A drone writes its `notes.md`. In a run that also writes the review record, the record wave still runs last (decision 12).

### UI prototype

12. **UI prototype.** An initiative whose PRD says `**UI:** yes` has a UI prototype, a required initiative artifact produced and approved after the PRD and before the solution design (#663). The PRD says WHAT the surface must do, the prototype what it looks like, and the solution design HOW it is built.
    - **UI line.** The first non-blank line after the PRD's `# ` title is exactly `**UI:** yes` or `**UI:** no`. Interrogation settles it, and `hivemind:plan-to-prd` writes it (#622). It is a recorded fact, read and never judged. The readiness check and stage derivation read a PRD with no `**UI:**` line there as `no`, so no PRD stamped before this decision must change. A `**UI:**` line there with any other value fails the readiness check with `prd_ui_invalid`. Verify fails a record the pull request adds or edits whose stamped PRD lacks a valid line (#619).
    - **Shape.** One self-contained `docs/initiatives/<slug>/prototype/index.html` that opens by double-click with no server, build or install, references nothing outside itself and implements every user story and screen the PRD's UI covers. Before approval it holds 3 to 5 structurally different variants, 3 by default, chosen by a `?variant=` URL parameter and a floating switcher, with realistic stub data in memory only and no polish. `docs/initiatives/<slug>/prototype/notes.md` holds one section per variant, describing it in words with the maintainer's feedback, and a verdict naming the chosen variant or combination and why. No design tool, hosted service, build step, framework or account is required (`docs/engineering-principles.md` P26). A published link may be added; the repository file is the source of truth.
    - **Approval, then refinement.** The maintainer reviews the variants and gives the feedback and the verdict as the answer to the guide's ask, the stage's approval gate (decision 8); the `## Verdict` section later written into `notes.md` is a progress marker, not that approval. The verdict is then folded into one approved variant in the same file. `notes.md` has no `## Verdict` heading until the refinement run; the refinement run writes the Verdict in its last non-record wave, after the changeling folds the variants; the build run writes no Verdict. On trunk `index.html` holds only the approved variant. The losing variants stay only in the docs pull request's history, and `notes.md` keeps their descriptions in words. This departs from the upstream prototype skill, which keeps a prototype off main as throwaway: here the approved prototype is a stamped artifact on trunk, because slices link to it and the readiness check verifies it.
    - **Review and stamps.** The design review covers the prototype (decision 6), and a passing record stamps both files (decision 7), so an edit to either after stamping makes the record stale. In a run that writes a prototype file and the review record, the record wave still runs last (decision 6, Review fix).
    - **Readiness.** Each slice of such an initiative carries exactly one Prototype line in its Design block, linking `docs/initiatives/<slug>/prototype/index.html`, its visual acceptance reference; a slice of any other initiative carries none. A missing line or file fails `prototype_missing`, and an unstamped file `record_unstamped:<path>`. The check judges structure and existence, never the prototype's quality. An initiative whose PRD says `**UI:** no` is otherwise unaffected.
    - **Order.** Stage derivation enters the UI prototype stage only when the PRD says `**UI:** yes`. A solution design before an approved prototype is out of order: the guide reports it and asks. `hivemind:prd-to-issues` refuses to slice such an initiative whose prototype is missing or not stamped by a passing record. The Design section, seed reuse, the Prototype line and the slicing refusal apply only when the epic `hivemind:prd-to-issues` resolves is the seed issue, whose marker names the PRD's slug: the readiness check's own binding of a slice to its initiative (decision 3). `subissue-ops.sh` tests that condition with the library's seed-marker parse on the epic body, which it reads itself, since `ensure-parent` returns no body; the guide names the seed issue number, passed as `--existing-number`. Otherwise it behaves as today, and its slices, initiative slices by decision 2, fail the readiness check: `epic_marker_missing` under an epic with no valid marker, `design_block_missing` under another initiative's seed.
    - **Standalone track.** Unchanged. A standalone change whose UI impact needs a prototype is promoted to the initiative track.
    - **Not the PRD's prototype exception.** The Prototype exception of `hivemind:plan-to-prd`, a labelled code sketch in the PRD of a throwaway prototype or spike initiative, is unrelated and unchanged.

## Considered options

- **Readiness stays a triage judgment.** Rejected: nothing a machine can repeat backs the label the Lair trusts.
- **Each caller writes its own readiness check.** Rejected: triage, the guide and the Lair would drift and disagree on one issue.
- **The track judged from the issue text.** Rejected: model judgment would decide what the Lair admits.
- **The guide as a workflow-engine workflow.** Rejected: workflows take no input mid-run and resume only in the same session.
- **The guide as an overlord section.** Rejected: it would load in every session and strain.
- **A stored progress pointer or ledger.** Rejected: the stage is derived from GitHub and git, on the same principle as the Lair.
- **A guide agent or a dedicated reviewer agent.** Rejected: the main-session conductor and fresh planner passes cover both.
- **A required second model.** Rejected: a second model is used only when configured; the cross-model pass reuses the configured local review tool, and the record names each pass's reviewer and model (PRD, #640).
- **Stamps by commit id.** Rejected: a squash or rebase merge changes the commit, while a blob id changes only with the content.
- **Moving the PRD into the initiative folder.** Rejected: PRDs stay where they live today.
- **Extending the interrogation skill's writer exception.** Not taken: a drone's exact file scope bounds each write with no new exception.
- **The readiness check parses the record body.** Rejected: the check stays a fixed front-matter parser, and verify checks the body before ready and in CI where a repository adds it.
- **Each caller passes its own trunk ref.** Rejected: a stale local main would pass.
- **Fix rounds kept off records by prose and agent reports.** Rejected: three review rounds found paths around it. The fix-round commit step refuses a record in code, and other commits stay prose-bound.
- **Refusing a record path in `molt.sh`.** Not taken: any agent writing a molt inputs file could set the allowing flag, and the github-reviewer commits with git, so it grows the surface and leaves the same residual (asked after design review round 4, answer Q15 A).
- **The guide passes verify as a validation command.** Rejected: a plan's validation commands are the planner's reading of the project's documented commands, so no code carries a guide-passed command to the validate step.
- **Stamps read at the branch head when the record is written.** Rejected: a commit between the clean pass and the record step, or a non-record wave in the pass run, would be stamped unreviewed.
- **A launch arg marking a guide run.** Not taken: it changes standard-delivery's launch contract, `readDeliveryLaunch` and the built script, while a fixed first request line needs no script change (answer Q19 A).
- **Guide runs fall back to Instinct.** Rejected: the guide re-derives the stage (answer Q19 A).
- **Review findings in a data block of the request.** Rejected: the request is a run's instruction channel and the pass scan reads only gathered texts, so a finding quoting hostile text or a fence would bypass it (re-review round 2).
- **A required CI merge gate.** Rejected: HIVEMIND must work in a project with only the plugin installed, so no feature may make the project add a CI workflow or a required check (`docs/engineering-principles.md` P26). A repository may add verify to its own CI as an optional capability (asked in re-review round 2, answer Q21 A).
- **Merge mode on the plugin's merge paths.** Not taken here: re-review round 4 found it pinned the merged head but not the base (RR4-C1), so merge-time enforcement is #619's own design question (answer Q25 A).
- **A throwaway sketch during interrogation.** Rejected: it leaves nothing durable to build against (#663).
- **The UI prototype as a section of the solution design.** Rejected: it puts UI and architecture in the same review round (#663).
- **Prototype variants mounted on an existing app route.** Not taken: a single HTML file works in every consumer project (`docs/engineering-principles.md` P26), and it may copy the host app's look (#663).
- **A new ADR for the UI prototype.** Not taken: the stage changes this ADR's process, so it is amended in place, as decision 8 was on 2026-11-22.

## Consequences

- A `readiness:ready` label on a slice now means its PRD, solution design, ADRs and review record exist on trunk and its record is current.
- Any edit to a stamped document fails every slice of the initiative until a review of the change re-stamps the record.
- The interrogation stage is the one single-machine window: its plan lives in the session or `.hivemind/`, so another machine sees only the seed issue.
- An initiative pays for design review rounds before slicing. One that has not converged after round 3 reaches the maintainer as a signal to split it.
- The readiness check depends on #625 for Lair admission and on the Lair controller (#608) to run at claim time.
- A docs pull request never takes the Lair's auto tier: #605 builds `docs/prds/`, `docs/initiatives/` and `docs/adr/` into its auto-tier floor.
- A slice whose solution design is delivered fails the readiness check (`design_delivered`).
- The council is not part of this process. A weak design decision is asked; #638 may change that only by its own ADR.
- A standard-delivery run the guide launched that fails or ends blocked returns to the guide, never to Instinct.
- A docs pull request whose record has an open finding or a failed verdict stays a draft under the guide, and neither GitHub nor `merge-approved.sh` merges a draft.
- Each design review round's findings appear as comments on the docs pull request.
- An initiative whose PRD says `**UI:** yes` pays for a UI prototype stage, with one maintainer approval, before its solution design, and each of its slices links the approved prototype.
- An edit to a stamped UI prototype file fails every slice of its initiative until a review of the change re-stamps the record.
- At claim the readiness check reads no GitHub of its own: its GitHub inputs are the claim snapshot's fields.
