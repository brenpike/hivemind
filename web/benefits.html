Why Adopt It

Problems Solved

Six real friction points in the plan-to-PR workflow, and how the Hivemind pipeline addresses each one.

01 Pipeline overhead

Managing the pipeline is its own job

Problem

Manually managing the plan → build → review → ship pipeline (deciding when to plan, when to build, when to stop and review) is cognitive overhead on top of the actual work.

Solution

The overlord is the control plane that coordinates specialized bioforms to plan, build, review, and ship code, so you don't have to manage the pipeline yourself.

Benefit

Less context-switching. A single interface. You give the overlord a task; the swarm handles the rest. 

Before:  You → plan → build → review → ship
         (every hand-off is manual)

After:
You → Overlord
       ├─▶ Cerebrate       (plan)
       ├─▶ Drone / Changeling  (build)
       ├─▶ Local-Reviewer  (review, if codex)
       └─▶ PR  (watched by default)
02 Planning vs building

Mixing planning and building leads to thrash

⚠️

Problem

When the same agent plans and builds simultaneously, it re-plans mid-implementation, second-guesses earlier decisions, and churns. The plan and the code drift apart.

🧠

Solution + Benefit

Separation of concerns: the read-only cerebrate plans (produces the directive), then drone and changeling build. Planning happens once, deliberately, before any code is written. Clearer reasoning; fewer mid-flight reversals.

Cerebrate is read-only
03 Unreviewed code

Code ships without a review gate

Problem

Without a built-in review step, code reaches the PR, or production, without being challenged. Adding an external review step is manual work that gets skipped under pressure.

Solution

Two separate review layers. Local pre-PR review needs the optional codex companion: the local-reviewer runs an adversarial Codex loop on the branch diff, fixing simple findings and escalating complex ones, before any PR exists. The post-PR watch is the default and does not need codex: after opening the PR, the overlord runs github-review-loop, which fixes, pushes, replies to, and resolves actionable feedback from Codex, Copilot, or Claude reviewer bots until approval, merge, or close. Agents never merge.

Benefit

A review gate built into the flow, not bolted on after the fact.

hivemind:local-reviewer hivemind:github-review-loop 
Build complete
 └─▶ Local-Reviewer  (pre-PR, needs codex)
      ├─▶ Codex review on branch diff
      ├─▶ Simple findings fixed
      └─▶ Complex findings escalated

PR opened  (watched by default)
 └─▶ github-review-loop
      ├─▶ Codex / Copilot / Claude bot feedback
      ├─▶ Fix, push, reply, resolve
      └─▶ Until approval, merge, or close
04 Serialised work

Large work is slow when tasks run one at a time

Problem

When independent work must be serialised through a single session, the pipeline becomes a bottleneck. Large features that could proceed in parallel wait on each other.

Solution

Parallelism at two scales. Within a run, plan steps build in parallel waves: every ready, dependency-met, file-disjoint step is dispatched at once, with one checkpoint per wave. Across runs, brood mode splits work into independent strains and, once you approve them, dispatches a brood: parallel overlord sessions, each running its own full lifecycle in a separate git worktree.

Benefit

Parallel throughput on independent work, inside a single run and across many. Each strain gets its own branch and PR.

hivemind:next-wave hivemind:spawn-brood hivemind:brood-status 
Within a run
Overlord
 └─▶ Wave  STEP-001 + STEP-002  (file-disjoint)
      └─▶ one molt

Across runs
Overlord  (hatchery mode)
 └─▶ Cerebrate  (decompose)
      │
      ├─▶ Strain A  ─┐
      │    └─▶ own branch, own PR │
      ├─▶ Strain B  ─┤  parallel
      │    └─▶ own branch, own PR │
      └─▶ Strain C  ─┘
           └─▶ own branch, own PR
05 Ad-hoc git hygiene

Git workflow is inconsistent without a system

⚠️

Problem

Without guardrails, branches are created informally, commits land with vague messages or not at all, and PRs open before validation passes. Every project drifts toward a different ad-hoc convention.

⚹️

Solution + Benefit

The overlord owns the git lifecycle: working branches, checkpoint commits (molts), and PR only after validation and versioning gates pass. Consistent, compliant history without manual discipline.

hivemind:create-working-branch hivemind:molt hivemind:open-plan-pr
06 Tooling lock-in

Rigid frameworks force you to adopt everything at once

Problem

Tooling that demands full buy-in up front, including specific review services, memory systems, or communication styles, blocks incremental adoption. If one dependency is absent, nothing works.

Solution

Optional companion plugins: claude-mem for cross-session memory, codex for local pre-PR review, caveman for token-compressed output. All optional. The framework works without any of them; if not installed, steps that depend on them are skipped gracefully. The theme itself is optional flavor: the framework works with or without it.

Benefit

Adopt incrementally. Start with the core pipeline; layer in companions when you need them. 

Core framework  ──────────────── always on
 ├─ overlord / cerebrate / drone / changeling
 └─ local-reviewer / github-reviewer

+ claude-mem    ─── optional (memory)
+ codex         ─── optional (pre-PR review)
+ caveman       ─── optional (compression)

Remove any layer → rest still works
🧠

claude-mem

Optional cross-session memory. When installed, the cerebrate reads claude-mem memory before every plan. Writes happen through automatic capture.

Optional
🔎

codex

Local pre-PR Codex review. Enables the local-reviewer agent. The post-PR watch is the default and runs without codex. If not installed, local review is skipped gracefully.

Optional
🕯

caveman

Token-compressed communication. When installed, all framework agents output in caveman ultra mode, reducing token usage while preserving full technical accuracy.

Optional
Get Started

Two commands inside Claude Code

No external install step. Add the marketplace, install the plugin, then run /hivemind:seed-hive once in each project. 

/plugin marketplace add https://github.com/brenpike/hivemind.git
/plugin install hivemind@brenpike
